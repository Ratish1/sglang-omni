## 2. The question of the smaller pool

The cap of plan 05 revision 6, a pool of running x context tokens in place of sglang's
fraction, was measured in readout 11 and dropped. What the measurement says:

- Throughput flat inside the paired spread at c1 and c16, quality inside the band, the
  process at ready 25 GB against 75 GB.
- The prefix cache: at c1 both pools keep every prefix hit of the corpus. At c16 the cached
  token count moves with prefill timing on both arms and is not a property of the pool size
  on this corpus.

So on this corpus the smaller pool is equal, not better. It is better only for what it frees,
memory for request time transients, which matters when a transient exceeds sglang's slack
(the gate of plan 05 section 4.8). It is worse whenever the reference working set of a
deployment is larger than the small pool, since the pool is the prefix cache: a request whose
reference was evicted pays its prefill again. That case is not in the benchmark and nobody has
measured it, so "the same or better for all scenarios" is not established and should not be
claimed. Main keeps the full pool. Bring the cap back only behind the plan 05 gate, with a
long reference corpus in the A/B.

## 4. How every slice is run

- One measured PR per issue on current upstream main. A is main, B is the branch with main
  merged. Boots interleaved A B B A, two per arm and point, one second samples of all GPUs.
  From 2026-09-09 the runs are unseeded with warmup 1, the real serving setting: full corpus at
  c1 and c16, WER and similarity, the kernel census at 1 and 16 rows with `perfkit.py`, and the
  streaming run at c16 in the CI layout, which is the main result, since most serving is
  streaming. Runbook 12 is the template for the steps, readout 13 for the readout, with the
  seed and warmup replaced.
- Streaming is reported as a delta table, A, B, delta: requests per second, audio seconds per
  second, time to first chunk mean and p99, inter chunk latency mean and p99, request latency,
  RTF, playback continuity at 200 ms, WER, completed. PR descriptions carry the best pair's delta
  tables, not every pair and not the boot protocol. PR #2057's body is the template.
- Gates: c1 byte identity 1088 of 1088 when the change is bit exact by construction, which needs
  one seeded c1 pass per arm for that check alone, unseeded sampling never matches. Otherwise
  the c16 band of 114 to 135 errors and 71.12 to 71.34 similarity. No regression on any metric
  beyond the paired spread. Peak memory read as a level from the samples, with the vocoder batch
  composition in mind.
- Tests: contract and edge cases, fakes with the real resolved shapes, no mock and count, no
  comments inside tests. Runtime code commits are discussed before they are made. Docs, tests
  and runbooks are pushed directly. Never patch sglang, sgl_kernel, torch or qwen-tts; close
  gaps at omni owned seams. No hardware specific constants.
- CI: the Qwen3-TTS streaming WER gate is crossed by a first round in about one job of six
  across all PRs, the stage retries and passes; the benchmark is unseeded. A first round
  overshoot on its own is not evidence about a branch.
