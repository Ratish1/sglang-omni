# Findings 2026-09-13

Plain list of everything observed so far, so nothing is lost. Each item names the code or PR.

1. Upstream main f58228dfb cannot boot Fun-CosyVoice3 with the default launch. `FlowCudaGraphRunner.capture` (`sglang_omni/models/fun_cosyvoice3/stages.py:415`, from #1861) calls `torch.cuda.graph(graph=...)`; torch 2.13.0 (the pin) names the parameter `cuda_graph`, so warmup raises TypeError. The unit test replaces the CUDA contexts on CPU, so CI never runs the real call. Fix PR: https://github.com/sgl-project/sglang-omni/pull/2147 (one keyword). Verified on H100: main plus the fix booted with graphs on and served four full English corpus cells.

2. Flow CUDA graphs cover only non-streaming finalize calls (`stages.py:630`: eager when `streaming or not finalize`). Every streaming hop runs the eager solver: 18.1k launches and about 300 ms host time per solve (perfkit). This is the streaming throughput ceiling. Plan slice V3.

3. HiFT recomputes the whole mel history every hop (`hift_delta`, `stages.py:1381`, concatenates `hift_mel` with the new frames). Per-request vocoder work grows with the square of the hop count. Plan slice V4.

4. Arm A (main plus the graph fix) on the English corpus, 1088 requests, warmup 1: streaming c1 1.23 req/s and 6.1 audio s/s, TTFC 0.46 s; streaming c16 1.37 req/s and 6.9 audio s/s, TTFC mean 11.1 s and p95 16.3 s, RTF 2.7, C50 98.7 with 14 underruns; non-streaming c1 2.18 req/s and 10.4 audio s/s; non-streaming c16 7.21 req/s and 35.1 audio s/s. Streaming c16 is serialized on the vocoder host thread. Comparisons are made A c16 against B c16 in the same mode, never c1 against c16.

5. Arm A had zero timeouts and zero failures at c16 streaming; the run on 645b472cd had 22 to 23 timeouts. Hypothesis, not verified: the streaming leftover call is `streaming=False, finalize=True`, so #1861 graphs it and finals got cheaper. The hop ledger on a B capture can confirm. Timeouts are no longer a discriminating gate; WER, TTFC and continuity paired against A are.

6. Arm B (our branch) did not boot on a GPU where a Qwen3-TTS process held 7,708 MiB. The process held 71.6 GiB when Flow and HiFT weights loaded. Cause: `mem_fraction_static: 0.85` in `sglang_omni/models/fun_cosyvoice3/engine_builder.py:122`. Pinned SGLang sizes the pool as free memory after weights minus 15 percent of pre-load memory (`python/sglang/srt/mem_cache/kv_cache_configurator.py:2007-2043`), so a 0.5B model gets a pool near 60 GiB and the vocoder must fit in the slack. Demand: Qwen2-0.5B has 24 layers, 2 KV heads, head dim 64, bf16, 12 KiB per token; 32 running requests times 4096 context is 131k tokens, about 1.5 GiB. Candidate fix, deferred and not part of the slice gate: cap the pool at the configured demand with `max_total_tokens = max_running_requests * context_length` (SGLang applies it at `kv_cache_configurator.py:2082`), optionally build the vocoder before the engine as #2042 did. Not our fault; B is rerun on an idle GPU first.

7. The 30 ms peer wait (`_first_hop_peer_wait_ms`) came in with #1656 without a measurement; #1899 measured coalescing overall, never the window. Removed on our branch.

8. PR #2086 fixes the deferred-chunk reordering (verified by NolanHo on 8xH200, zh, with Flow graphs off because of item 1). Nobody in its thread measured throughput; the reported speed decline has no numbers yet. Our branch sits on upstream main and carries only 2086's 24-line shared-base change as its own commit.

9. The team's "2 to 3 percent SM" is not SMs Active in any capture; only Tensor Active sits at 2.5 to 3.3 (results doc section 0).

10. Gate protocol for the rerun: A is main plus the graph fix (first commit of the branch), B is the branch head, one boot per arm on idle dedicated GPUs, default launch with graphs on, English corpus, unseeded, warmup 1, c1 and c16, streaming and non-streaming, WER paired per cell.
