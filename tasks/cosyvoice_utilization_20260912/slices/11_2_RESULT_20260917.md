# Slice 1.2 on the 4090: what the runs say, and why it does not merge

Runs on 2026-09-17, moss box, cards 4 and 5, RTX 4090 D 24 GB, head `84e745ea`
(slice 1.2 on slice 1.1 on main `27a8293c`), 16 or 32 English SeedTTS samples,
streaming, seed 1234, warmup 1, one server per arm, one arm at a time.

## The cache works, and at c1 it is worth 3 percent

Same head, same card, cache off against cache on at 2 GiB (2,383 frames). 35 hops
each, every hop cached, no fallback, no exhaustion.

| | cache off | cache on | delta |
|---|---|---|---|
| RTF mean | 0.2441 | 0.2376 | -2.7% |
| RTF p99 | 0.3175 | 0.3162 | -0.4% |
| first audio mean | 0.585 s | 0.562 s | -3.9% |
| req/s | 0.834 | 0.860 | +3.1% |
| audio s/s | 4.343 | 4.475 | +3.0% |

This is what G0 predicted for c1 and it is not a disappointment: the cached hop
call is flat at the eager launch floor, so at c1, where windows are short, there
is little device work to remove. The plan's case has always been c16.

## This card cannot run the concurrency the case rests on

| point | cache | completed | failed | RTF mean | note |
|---|---|---|---|---|---|
| c1 | off | 16 | 0 | 0.2441 | |
| c1 | on, 2 GiB | 16 | 0 | 0.2376 | 35 hops, 0 fallbacks |
| c4 | off | 31 | 1 | 0.4861 | 2 CUBLAS handle failures |
| c8 | off | 23 | 9 | 0.7149 | 20 CUBLAS handle failures |
| c8 | on, 2 GiB | run aborted | | | 16 fallbacks, then the same failure |
| c8 | on, 6 GiB | run aborted | | | CUDA OOM inside the AR sampler |

The c8 and c4 failures are **not** the cache: they happen with it off, at the
same place, and they are the roadmap's B1 row. The reference encoder's ONNX
speech tokenizer cannot create a cuBLAS handle
(`request_builders.py:296` to `utils.py:92`) because SGLang has already sized its
KV pool from whatever memory was free, and nothing reserves anything for the ONNX
sessions or for the sampler's transient allocations.

So on this hardware there is no paired point above c1 to measure the cache at,
and the 6 GiB arm shows the second half of the same problem: bytes taken by the
Flow pool come straight out of that margin, because the vocoder is built first by
design (`config.py:144-146`).

## What this means for the slice

1.2 is implemented, correct and tested: 212 unit tests pass, the cached hops run
clean at c1, the fallback path releases and recomputes exactly as designed when
the pool cannot grow a stream (16 fallbacks at c8, no crash from the cache), and
G0 already settled the numerics. It is also, on the only hardware available,
worth 3 percent and unmeasurable where it claims 30.

It does not merge on this evidence. The branch stays at
`slice/cosyvoice-1-2-hop-cache`, no PR.

## Two things the runs make plain

**The memory provisioning defect outranks it.** A server that drops 1 of 32
requests at c4 and 9 of 32 at c8, on unmodified code, is a correctness problem
sitting above every performance question in this task. Nothing in the roadmap
owns it beyond the B1 line, and it is reproducible here in 90 seconds.

**The hop cache is one third of the real fix.** The vocoder's defect is that a
hop recomputes its whole prefix, and that appears twice. Flow is the half this
slice fixes. HiFT is the other half and is untouched: `hift_delta` concatenates
the entire mel history and reruns HiFT over all of it every hop, keeping only the
tail (`stages.py:1679-1683`), and `plans/04_hift.md` H2 parks it as an
investigation. The third term is the 19,072 eager launches per Flow call, which
is what the cached call's flat 140 ms is made of. Landing one of the three and
measuring 3 percent is the expected outcome, not a surprise.
