# Sector 08: profiling mechanics and diagnostic-script audit

## Scope and evidentiary boundary

This report describes the checked-out SGLang-Omni baseline and the separate SGLang baseline named in `RESEARCH_CONTRACT.md`. It reports code-visible behavior only. No profiler, benchmark, test, or model process was run. PyTorch/Kineto, CUPTI, Nsight CLI, and Nsight SQLite behavior that is not fixed by these repositories remains an external runtime boundary.

## Ownership and call graph

### SGLang-Omni HTTP and stage control

`POST /start_profile` is owned by `sglang_omni/serve/launcher.py:265-316`. It creates/accepts a run ID, resolves the event directory and trace template, starts the coordinator's process-local event recorder, calls `ProfilerControlClient.broadcast_start`, and returns. `/start_request_profile` follows the same path with `enable_torch=False` (`launcher.py:318-348`). Stops close the coordinator recorder first, broadcast a stop, and return (`launcher.py:350-370`).

`ProfilerControlClient.start` opens a `PushSocket` per stage endpoint; `broadcast_start` and `broadcast_stop` sequentially send one message to each named target (`profiler_control.py:24-32,41-87`). The `config` argument accepted by `broadcast_start` is not placed in `ProfilerStartMessage` or otherwise consumed. Unknown requested stage names are silently skipped. The calls await socket sends only. There is no reply, barrier, acknowledgement message, recorder path response, or stage error result in this protocol.

Each `Stage.run` task receives its own control messages on the process asyncio event loop, TP leaders fan the message out before handling it, and `_handle_message` invokes synchronous `_on_profiler_start`/`_on_profiler_stop` (`runtime.py:320-385`). A stage starts torch profiling only if the process-global `TorchProfiler.is_active()` is false; it always attempts to join the event recorder when `event_dir` is present (`runtime.py:1792-1811`). A stop stops the process-global torch profiler and recorder if the optional run ID matches (`runtime.py:1813-1823`).

All colocated stages share one OS process and one asyncio loop, but each owns a dedicated scheduler thread (`runtime.py:70-85,204-250`; `stage_workers.py:456-510`). `TorchProfiler` stores `_profiler`, `_trace_template`, `_active_run_id`, and `_lock` as class attributes (`torch_profiler.py:31-42`). Consequently, in a process containing three stages, the first stage control task that handles start creates the only Kineto instance and determines its trace template. Later stage handlers see it active and skip `start`. The first matching stage handler that handles stop stops and clears the only instance; later handlers see it inactive. The code has no shared-process refcount, per-stage participation set, or stage-control barrier. The JSONL recorder has explicit shared-process join semantics, unlike the torch profiler.

The control handler runs on the asyncio/control thread. Actual scheduler/model work runs on `scheduler-<stage>` threads (`runtime.py:212-248`). The Omni code does not enter a profiler context or call `TorchProfiler.start` on those scheduler threads. The profiler requests CPU and CUDA activities, but whether and how a pinned PyTorch/Kineto release records CPU operator spans and CUDA launches initiated by other process threads is not established by repository code. There is therefore no code-level guarantee that the default trace contains CPU operator attribution from the actual worker threads. CUDA activity process scope and cross-thread correlation are unresolved external runtime semantics.

The HTTP start response means all messages were sent, not that every stage process has started recording. The HTTP stop response likewise means stop messages were sent, not that stages stopped, traces exported, or gzip children completed. `TorchProfiler.stop` performs `profiler.stop()` and explicit JSON export synchronously in a stage event-loop handler, launches `gzip -f` without waiting, clears class state, and returns an expected `.gz` path (`torch_profiler.py:137-196`). Thus the effective per-process interval begins when that process eventually handles start and ends when its first matching stage handles stop; intervals can differ across processes and from the client interval.

### SGLang engine profiler

SGLang exposes both GET and POST for `/start_profile`; the optional body is a `ProfileReq`. `/stop_profile` accepts no profile body. Both routes await the tokenizer-manager call before returning a plain-text 200 response (`http_server.py:1171-1190`). `ProfileReq` is a tagged, keyword-only, array-like `BaseReq`/`msgspec.Struct` IPC payload. It carries the request type, output directory, step and stage-window controls, activities, stack/shape flags, profile/run naming, merge controls, selected stages, and detailed-annotation flag; `ProfileReqOutput` carries `success` and `message` (`io_struct.py:65-75,2105-2141`). The file's import-time type check enforces request naming and `BaseReq`/`BaseBatchReq` inheritance, and its generic socket helpers serialize those registered structs through msgpack unless pickle IPC is enabled (`io_struct.py:2361-2497`). There is no profile-specific value validation in these definitions. In particular, the `activities` field comment lists `CPU`, `GPU`, `MEM`, and `RPD`, while the profiler managers also recognize `CUDA_PROFILER`.

The tokenizer creates the profile `FanOutCommunicator` in the default `queueing` mode, initially with DP-size fanout; `update_control_communicator_fan_out` later assigns `worker_count` to it (`tokenizer_control_mixin.py:100-131,161-190`). Start applies environment gates to `with_stack` and `record_shapes`, assigns a time-string `profile_id` if absent, and delegates to `_execute_profile`; stop constructs a `STOP_PROFILE` request (`tokenizer_control_mixin.py:380-407`). `_execute_profile` awaits the communicator call, indexes element zero of its returned list, and raises only if that first `ProfileReqOutput` reports failure. This route therefore has a returned scheduler-result path, unlike Omni's PUSH-only protocol, but this layer neither merges all profile results nor checks failures in list elements after index zero. The scheduler dispatches each received `ProfileReq` to `SchedulerProfilerManager._profile` on its request loop (`scheduler.py:1683-1684`).

`http_server.py` also exposes `/server_info`, which awaits live internal state and combines resolved server arguments, scheduler information, startup time, version, and KV-event publishing description (`http_server.py:811-840`). Its `/set_trace_level` changes the independent observability trace level; lifespan initializes process OTLP tracing and labels the tokenizer thread only when `enable_trace` is set (`http_server.py:270-304,1192-1200`). Those observability controls do not alter Kineto profiler activities. The rest of the fully read HTTP server, tokenizer control mixin, and IPC structure file consists of server lifecycle plus inference, health, cache, weight, LoRA, session, distributed, and other control/data routes; those routes do not participate in the profiling control chain described here.

Legacy `SchedulerProfilerManager` rejects a second active configuration, maps requested `CPU` and `GPU` to PyTorch activities, supports memory history, ROCm RPD, and a `CUDA_PROFILER` activity that calls `cudaProfilerStart/Stop` only on the base GPU rank (`profiler_manager.py:87-160,168-279,313-406`). The default is `CPU,GPU`; legacy defaults `with_stack=True` and `record_shapes=False` after tokenizer normalization normally makes both true unless request/environment disables them. Step and stage predicates control delayed/finite windows (`profiler_manager.py:408-446`).

With `SGLANG_PROFILE_V2`, `ProfileManager.configure` currently asserts `start_step is None`, `profile_by_stage` is true, and merge is false. `manual_start` and `manual_stop` raise `NotImplementedError`; stage transitions drive `_do_start/_do_stop` (`profile_utils.py:73-185`). `_StageBasedTrigger` counts observed prefill/decode stages and stops on count beyond target or a stage transition (`profile_utils.py:191-241`). Concrete activities are composed in `_ProfilerList`: Torch, memory, CUDA profiler API, and RPD (`profile_utils.py:247-460`). In v2, `CUDA_PROFILER` calls are restricted to `first_rank_in_node`, computed from `gpu_id == base_gpu_id` (`profile_utils.py:73-84,407-416`).

Omni's `StartReq.config` superficially resembles configurable profiling, but it is dropped by `ProfilerControlClient`. Omni always instantiates Torch profiler with exactly CPU and CUDA activities and only its four `SGLANG_TORCH_PROFILER_*` boolean flags (`torch_profiler.py:116-128`). It exposes none of SGLang's activities selection, `CUDA_PROFILER`, stage windows, finite step triggers, detailed step annotations, or rank merge controls.

## Profiler implementations and exact symbol mechanics

### `event_recorder.py`

Imports/constants and active-stage state occupy lines 1-35. `set_active_stage` (38-41), `reset_active_stage` (44-50), and `get_active_stage` (53-58) maintain both a `ContextVar` and `threading.local`, preferring the context variable. Reset with a token restores only the ContextVar's prior value and unconditionally clears the thread-local slot; nested bindings therefore do not restore identical state in both stores. The comment/docs assertion that `loop.run_in_executor` copies context variables is not implemented here and is not true of plain executor submission by virtue of this code; only callers that explicitly propagate a context have such behavior. The dedicated scheduler thread is directly bound at startup.

`RequestEvent` (62-74) is the serialized point event. `RequestEventRecorder` (77-219) owns one append-mode, line-buffered JSONL file per process. `start` joins the same run ID by adding a stage, rotates on a different run ID, creates directories, and names the file from the first joining stage and PID. `stop` accepts a wildcard, ignores a mismatched explicit run ID, flushes/closes, and clears state. `emit` is inactive-fast-path/no-op, defaults `timestamp_ns` to `time.time_ns`, resolves a missing stage from task/thread binding then the first stage then `unknown`, writes two pieces under a lock, swallows write failures, counts drops, and logs only the first failure. It does not expose the drop count.

`_json_default` (222-251) emits scalars for zero-dimensional objects with `.item()`, summaries for shape/dtype objects, and `repr` for others. The module singleton/accessors occupy 254-277. `_read_host_boot_id` (281-288) caches Linux boot identity. `_emit_model_path` and wrappers (291-312) emit a wall-clock event whose metadata separately contains `CLOCK_MONOTONIC`, boot ID, and `time.monotonic_ns()`.

### `torch_profiler.py` and base class

`ProfilerBase` (16-58) declares start, stop, step-context, active-state, and rank-from-`RANK` contracts. Its annotated abstract start/stop signatures do not include `run_id` and say stop returns a path, whereas concrete Omni methods accept `run_id` and return a dict.

`TorchProfiler` (31-209) is process-global class state. `start` (49-134) locks, attempts same-run idempotence or active-session cleanup, computes rank/template, creates the directory, constructs continuous `torch.profiler.profile` for CPU+CUDA with environment-selected shape/memory/stack/FLOP flags, starts it, and returns an expected gz path. There is a code-proven local-variable defect: every active-profiler branch references local `rank` at lines 58, 62, and 70 before `rank = cls._get_rank()` at line 76. A direct repeated/replacement `start` while active raises `UnboundLocalError` before either idempotent return or cleanup. The normal stage handler avoids this branch by checking `is_active` before calling `start`; that avoidance is not enforced by `TorchProfiler.start` itself.

The nested `trace_handler` exports and starts gzip if PyTorch invokes it. `stop` also calls `profiler.stop`, explicitly exports the same JSON path, and starts gzip because its comment states the callback is not fired without a schedule. Whether the installed PyTorch invokes `on_trace_ready` on this stop configuration, and therefore whether both export paths can run, is external version-specific behavior; code inspection cannot establish duplicate-export reachability. `step` delegates, `is_active` tests the singleton, and `get_step_context` is always a null context.

`TorchNPUProfiler` (212-297) uses NPU CPU/NPU activities and a tensorboard trace handler; it has the same class-state model and active cleanup but computes rank before active checks. It is unrelated to reachable CosyVoice CUDA behavior.

### `profiler_control.py`, `comm_trace.py`, CLI, and views

`ProfilerControlClient` is covered in the ownership graph. `comm_trace.enabled/now_ns/elapsed_ms/emit` (15-33) are an independent environment-gated logger: durations use `perf_counter_ns`, emitted timestamps use `time.time_ns`, and records are JSON embedded in log messages. They are neither NVTX nor request JSONL.

The CLI `_main` (19-66) calls `build_report`, formats JSON or two fixed-width tables, and writes stdout or a file. `views.iter_events/load_events` (26-61) discover only `events_*.jsonl`, skip malformed JSON lines, and globally stable-sort by optional wall timestamp. They do not validate schemas or filter `run_id`.

`RequestTimeline` (70-108) takes the first/last sorted event as bounds. `reconstruct_timelines` (111-125) drops falsey request IDs. Documentation says relative time is anchored at admission, but implementation anchors it at the earliest retained event; it never locates `request_admission`.

Stage interval declarations are 133-148. `StageInterval` (152-164), `StageBreakdownRow` (168-188), `_percentile` (191-202), `compute_stage_intervals` (205-252), and `stage_breakdown` (255-282) use FIFO lists scoped by request, stage, opener, and closer. Multiple pairs get independent queues. Unmatched endpoints are silently omitted. Percentiles use linear interpolation over sorted samples. Durations derive from `time.time_ns` across process files; the additional monotonic metadata on model-path events is ignored.

`HopBreakdownRow` (290-313) and `hop_breakdown` (316-385) pair FIFO sends/receives by request/source/destination/kind/chunk ID, exclude coordinator payload input, and silently omit unmatched records. `build_report` (393-401) produces all views; `format_table` (404-416) performs string-width formatting. Reusing an append-mode event directory across runs, or combining files with the same request ID, causes cross-run grouping because no run-ID partition exists.

### `asr_profiling.py`

Profile HTTP wrappers (35-56) use 30-second requests with proxies disabled. `run_profiled_pass` (74-125) starts URLs sequentially, rolls back those already started on request failure, executes the pass, and stops sequentially in `finally`; stop errors are printed and pass results retained. Because Omni responses do not acknowledge stage activation or flush, these calls do not establish an exact server-side event window. It builds the report immediately after stop responses, so late stage stop handling/writes can race report loading.

`build_stage_breakdown` (59-71) optionally drops timelines. `UtilizationSummary` (129-143), proc-stat reader (146-158), GPU query (161-189), and `UtilizationSampler` (193-273) sample system-wide host CPU deltas/load and `nvidia-smi` device-index utilization/memory. The first sample occurs only after one interval; subprocess failure yields no GPU sample. `stop` joins with a timeout but clears `_thread` even if it remains alive. GPU means are unweighted arithmetic means of successful queries.

Command/package helpers (276-301), server identity (304-325), environment fingerprint (328-369), cached HF revision (372-385), and JSON writer (388-391) are best-effort client evidence. Server identity records only model IDs and URL; it does not establish server code SHA/configuration.

## Existing observability and clock/range semantics

SGLang's `nvtx_utils.py` imports the external `nvtx` package only when scheduler or operations flags were true at module import. `profile_range` (84-97) emits `torch.profiler.record_function` only when `torch.autograd._profiler_enabled()` is true in the calling context, and independently emits an NVTX annotation when the subsystem gate and package allow it. The scheduler has decorated host regions for request processing, batch selection, batch execution, and result processing (`scheduler.py:1965,3334,4012,4356`). These are host lexical ranges; repository code does not treat them as CUDA completion timestamps.

`PytHooks` (`nvtx_pytorch_hooks.py:20-292`) recursively records tensor dimensions, layer parameters, pushes an NVTX range in a forward pre-hook, pops in the forward hook, and registers hooks on every named module except identity/dropout types. It is opt-in through explicit `register_hooks`; no CosyVoice registration was found. Exceptions during a module forward can leave a pushed range because the post-hook is not registered with an always-call guarantee in this code.

No `record_function`, `torch.cuda.nvtx`, or `nvtx` callsite exists in `sglang_omni/models/fun_cosyvoice3`. Therefore a CosyVoice Nsight trace has no existing Omni Flow/DiT/HiFT stage NVTX ranges. SGLang scheduler NVTX can label the embedded AR engine only if its import-time flag and package conditions are met. Omni request events provide stage attribution in separate JSONL wall-clock files, not ranges embedded in an Nsight trace.

Graph-capture tracing is separate. SGLang's `export_cuda_graph_capture_trace` (`profile_utils.py:52-70`) is gated by `SGLANG_ENABLE_CUDA_GRAPH_CAPTURE_TRACE` and exports a capture-time Chrome trace, namespaced by runner and TP rank. It does not make an Nsight replay trace node-granular. The upstream SGLang Nsight example explicitly uses `--cuda-graph-trace=node` and `--trace-fork-before-exec=true` (`examples/profiler/nsys_profile_tools/README.md:56-73`). The supplied CosyVoice `nsys launch` command includes neither flag (`PLAYBOOK.md:203-224`). Actual graph-node and descendant coverage therefore depends on installed Nsight defaults/runtime behavior and is not guaranteed by the supplied command text.

## SGLang trace merge mechanics

`ProfileMerger` (14-199) discovers gz traces matching `<profile_id>*.trace.json.gz`, excludes merged/memory files and any name lacking `TP-`, then processes them in DP/EP/PP/TP rank order. Per-file read/JSON failures are logged and converted to empty event sets, so a merged file can succeed while silently excluding a rank. It concatenates trace events without clock alignment, changes every event PID to a rank-labelled string, adjusts `process_sort_index` only when its PID casts to an integer below 1000, concatenates every file's device properties, and takes each other top-level field only from the first file containing it. It does not rewrite TIDs, correlation IDs, device IDs, timestamps, flow IDs, or references embedded in args. Summary counts discovered source files, including files that failed to contribute events.

The upstream `gputrc2graph.py` is a different postprocessor. It asks `nsys stats` for `cuda_gpu_trace`, globally sorts all rows by start, allocates incremental non-overlapped elapsed time to the kernel whose row extends the current union, groups by kernel name, then subtracts union GPU seconds from a separately supplied unprofiled wall time. It does not partition devices or analysis windows. Its regex classification JSON covers Llama/DeepSeek/GPT-OSS only, not CosyVoice. Its README says an elapsed value of `0` uses elapsed time from the Nsight report (`README.md:19-21`), but the implementation never reads such a duration: it rounds `0`, replaces it with `gpu_sec` because it is smaller, and emits zero CPU/non-GPU time (`gputrc2graph.py:269-280`). An empty CUDA trace also reaches `ends[0]` in `sum_non_overlapping_intervals` (`gputrc2graph.py:74-85`) rather than producing an empty result.

## Supplied Nsight SQLite analyzer: formula, errors, limitations

`quote_ident` (19-20) doubles identifier quotes. `summarize` (23-94) requires ordered intervals and a positive explicit window/top-gap limit. For every positive-duration row intersecting the window it clips to `[start_ns,end_ns)`, adds clipped raw duration, extends a sweep-line union, and records uncovered intervals including window edges. Its central formulas are:

* `union_fraction = captured_kernel_union_ns / (end_ns - start_ns)`;
* `sum_over_union_overlap_factor = sum(clipped durations) / union_ns` when nonzero;
* `no_captured_kernel_ns = window_ns - union_ns`.

These are internally consistent kernel-timeline union quantities. They do not calculate SM active, occupancy, FLOPs, copy-engine activity, CUDA API blocking time, per-process shares, or causal attribution. All selected contexts/processes are combined solely by exported `deviceId`; the output cannot identify which process produced a covered interval. Gaps can contain memcpy/memset, CPU submission, synchronization, graph work absent from the kernel table, or uncaptured processes.

`open_database` (97-102) uses SQLite URI `mode=ro` plus `query_only`. `choose_table` (105-123) auto-supports only `CUPTI_ACTIVITY_KIND_KERNEL` and `CUPTI_ACTIVITY_KIND_CONCURRENT_KERNEL`, rejects multiple populated candidates, rejects no populated candidate, and case-normalizes only required column names. An explicitly requested table need not be a kernel table and need not be populated; any table with `start,end,deviceId` passes. Other Nsight schema/table variants are rejected rather than adapted.

`devices` (126-131) returns row counts and min/max bounds, which omit outer idle time. `main` (134-167) requires integer device/start/end unless describing, validates device presence anywhere in the table, queries intersecting rows ordered by start/end, and emits JSON. SQL/OS/Value errors become exit 2. A `NULL` timestamp reaches `int(None)` in `summarize`, raising `TypeError`, which `main` does not catch. Very large integer differences are exact through union arithmetic, but seconds/fractions/percentages are emitted as binary floats.

The ten `unittest` methods (`test_analyze_nsys_sqlite.py:8-65`) cover overlap, empty window, clipping, nesting, invalid/equal window, unsorted input, large timestamps, outside rows, gap limit, supported schema selection, device catalogue, and read-only enforcement. They do not cover CLI handling, NULLs, multiple candidate tables, explicit non-kernel tables, alternate schemas, graph records, process/context attribution, or real Nsight exports. No tests were run for this report.

## Exact mismatches and evidence gaps in the supplied diagnostic bundle

1. `PLAYBOOK.md:205` says launching the actual server places worker descendants in scope, while its command omits the `--trace-fork-before-exec=true` used by upstream SGLang and omits upstream's `--cuda-graph-trace=node`. Descendant and graph-node completeness is therefore not established by repository code or command text.
2. The playbook says to inspect large gaps beside NVTX ranges (`PLAYBOOK.md:251`), but CosyVoice has no existing NVTX/record-function stage instrumentation. Only optional embedded SGLang scheduler ranges are present, conditional on import-time environment and package availability.
3. The native Omni HTTP profiler cannot provide a common acknowledged multi-process window. Start/stop endpoints return after PUSH sends, shared processes stop at the first stage stop handler, and gzip completion is asynchronous. Documentation lines 128-151 and 190-219 describe lifecycle/results without these acknowledgement and shared-process limitations.
4. Documentation says the torch profiler yields a gzip trace on stop (`profiler.md:190-195`), but the HTTP stop does not await stage stop/export, and stage export does not await gzip. The returned expected path can precede file existence/compression completion.
5. Documentation's serving-safety statement (`profiler.md:231-234`) accurately describes event emitter write failures, not the entire profiler path. `_on_profiler_start` does not catch `TorchProfiler.start` exceptions; an exception propagates through the stage run loop and can fail its shared stage process (`runtime.py:332-361`; `stage_workers.py:463-469`).
6. `StartReq.config` is exposed and documented in the Omni HTTP body but discarded. It cannot select SGLang-style activities, CUDA profiler API gating, stage ranges, or trace options.
7. The request-view documentation calls `t_rel_ms` admission-anchored; implementation uses the earliest event. Views do not partition by `run_id`, validate clocks/host identity, expose unmatched pairs, or consume model-path monotonic metadata.
8. `run_profiled_pass` immediately reads JSONL after unacknowledged stop sends. Its reported request/stage/hop data can omit events still buffered or emitted before a stage eventually handles stop. It also catches only request exceptions during teardown; report parse/shape failures propagate.
9. `analyze_nsys_sqlite.py` correctly labels its metric as captured-kernel union, but the capture command does not guarantee child/graph completeness, and the analyzer cannot detect those omissions. It also cannot distinguish another captured process on the same exported device from serving work.
10. `run_sweep.sh` invokes arguments supported by this baseline's `benchmark_tts_seedtts.py`, uses pipefail, and refuses directory reuse. It does not start/stop profiling, establish a trace window, record resolved server configuration, capture raw counter streams, or separate server state between points. Each failed benchmark leaves its newly created target directory non-reusable.
11. `collect_env.py` writes a snapshot and does not load a model. It hashes six Omni CosyVoice files and records the Omni package Git root, but it does not resolve/hash the separately installed SGLang source, a server PID, server thread affinity, live resolved stage configuration, live backend/fallback state, or a checkpoint revision. Its collector-process affinity/cgroup evidence is not server-process evidence; the README acknowledges the config distinction.
12. `experiment_template.json` has fields for selected trace window and coverage fraction but no structured fields for profiler start/stop acknowledgements, captured PID/context set, Nsight version/export schema, CUDA graph trace mode, kernel table, invalid interval count, or unmatched event-pair counts. Null placeholders are records to fill, not evidence those facts were captured.

## Facts versus unresolved runtime evidence

Code establishes ownership, requested activities, asynchronous message routing, process/thread topology, file formats, formulas, and error handling. It does not establish the installed PyTorch/Kineto thread/process capture semantics, whether `on_trace_ready` fires in this unscheduled configuration, the installed Nsight CLI defaults, exported schema, graph-node representation, descendant injection, clock calibration among JSONL and Nsight, captured process set, effective model configuration, actual GPU/device mapping, dropped CUPTI records, profiler overhead, or any target runtime duration/utilization/root cause. Those remain unresolved external/runtime evidence.
