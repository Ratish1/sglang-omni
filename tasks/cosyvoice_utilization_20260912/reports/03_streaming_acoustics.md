# Sector 03: streaming acoustics

## Scope and ownership

This sector follows the Fun-CosyVoice3 AR speech-token producer into the shared streaming scheduler, the model-specific causal Flow/HiFT scheduler, and the buffered vocoder route. The assigned owners were read completely. `request_builders.py`, the state serialization layer, stream queue, audio serialization, and request protocol were also read completely because they own state initialization or a directly consumed wire contract. Relevant regions of `stages.py`, `engine_builder.py`, `omni_scheduler.py`, and stage `runtime.py` were read as boundary evidence; those files have broader owners and are recorded as partial coverage.

The in-repository ownership chain is:

1. Preprocessing constructs aligned Flow prompt tensors and stores them in `FunCosyVoice3State`; the AR request builder transfers them into `CosyVoice3SGLangRequestData` and conditionally enables streaming metadata (`request_builders.py:556-575`, `request_builders.py:626-701`, `request_builders.py:742-817`).
2. `FunCosyVoice3ModelRunner` samples one speech token per AR step, retains every usable token for the terminal payload, and emits code chunks to target `vocoder` when its producer thresholds are reached (`model_runner.py:96-183`).
3. The stage runtime gives each emitted target chunk a monotonically increasing per-request/target `chunk_id`, routes it, then on the AR terminal result sends `stream_done` before forwarding the final `StagePayload` to the vocoder (`runtime.py:1092-1149`, `runtime.py:1171-1231`, `runtime.py:1445-1505`).
4. `StreamingSimpleScheduler` accepts stream chunks and done signals before the payload. `StreamingVocoderBase` owns per-request state creation, validation, terminal ordering, fallback, abort, and release. `FunCosyVoice3StreamingVocoderScheduler` owns token/hop cursors, prompt latching, causal-step admission, Flow invocation, and HiFT continuation state (`streaming_simple_scheduler.py:470-519`, `scheduling/streaming_vocoder.py:164-377`, `models/fun_cosyvoice3/streaming_vocoder.py:126-859`).
5. The `stages.py` boundary owns packed Flow computation and the concrete `_CosyVoice3Vocoder` calls. The external CosyVoice package owns the wrapped native Flow `inference` and HiFT `inference` implementations; this report states only their call contracts visible at the repository boundary (`stages.py:93-532`, `stages.py:939-1242`).

The default pipeline is `preprocessing -> tts_engine -> vocoder`. `tts_engine` has both `next="vocoder"` and `stream_to=["vocoder"]`; the vocoder is terminal and permits stream data before its payload. Default producer hop is 25. Default vocoder hop starts at 25, grows to at most 100, has batch size 16, buffered batch wait 30 ms, and buffered Flow admission cost 8,000 mel frames (`config.py:32-94`). `engine_builder.py:126-143` constructs the runner with the configured hop and gives it the scheduler's outbox.

## Token production, buffering, and terminal flush

`FunCosyVoice3ModelRunner._collect_tokens` is called after both prefill and decode. Both sampling hooks return true, so sampling precedes the corresponding post hook (`model_runner.py:58-94`). If `next_token_ids` is absent, collection stops. A non-rank-one result is flattened, then the entire batch is converted with one `tolist()`. For each request row, IDs at or above `VOCAB_SIZE` are excluded from `output_codes` and from streaming; IDs below it become fresh CPU `torch.long` tensors of shape `[1]`, are appended to `output_codes`, and are offered to the stream buffer (`model_runner.py:96-116`). The `tolist()` is the explicit batch device-to-host value materialization in this path.

Streaming production is enabled only when both the runner outbox exists and `stream_metadata` is non-null. `build_cosyvoice3_stream_metadata` requires `payload.request.params` to be a dict and returns `{"modality": "audio_codes", "stream": True}` only for truthy `params["stream"]`; it does not consult `FunCosyVoice3State.stream` (`streaming.py:199-211`). The request builder installs this result after creating request-local state (`request_builders.py:802-817`).

Each usable token increments `stream_code_seen` and enters `stream_code_buffer`. On the first token, `stream_code_next_flush` becomes `first_ar_flush_tokens(...)`. Although the caller passes the Flow prompt length, the helper discards it and returns `hop_len + 3`; with the default hop this is 28. A threshold flush concatenates all pending `[1]` tensors along dimension zero, clears the list, sets the next threshold to current cumulative seen count plus 25, and enqueues one `OutgoingMessage(type="stream", target="vocoder")`. Producer chunk sizes are therefore 28 for the first chunk and 25 for subsequent threshold chunks (`streaming.py:97-107`, `model_runner.py:118-183`).

The first emitted code chunk copies the base metadata dict and adds `flow_prompt_speech_token`, `flow_prompt_speech_feat`, and `flow_embedding`; `stream_prompt_sent` is then set. Later code chunks carry only the base metadata. Tensor objects are attached directly to the message; no clone or device conversion occurs in `_emit_code_chunk` (`model_runner.py:156-183`).

When the AR request finishes, `on_request_finished` force-flushes any nonempty residual producer buffer. A force flush does not advance `stream_code_next_flush`, which is immaterial after terminalization. In `OmniScheduler`, this hook runs before final stream-output-builder flushing, result adaptation, request cleanup, and enqueueing the AR terminal result (`model_runner.py:45-46`, `omni_scheduler.py:1675-1737`). The stage runtime drains the same FIFO outbox. When it reaches the result, `_route_result` awaits a done signal to each stream target before sending the final payload to the next stage (`runtime.py:1092-1149`, `runtime.py:1171-1231`). Thus residual code chunks precede `stream_done`, and `stream_done` precedes the vocoder's terminal payload at this boundary.

`apply_sglang_cosyvoice3_result` stacks `output_codes`, casts/concatenates them as long, and moves the aggregate to CPU; an empty generation produces an empty CPU long tensor. It writes `audio_codes`, prompt/completion counts, elapsed engine time, and sample rate into the terminal state (`request_builders.py:820-850`).

## Prompt construction and hop alignment

Reference preprocessing first aligns Flow conditioning to two mel frames per prompt token. `_align_flow_prompt` requires prompt tokens shaped `[1, tokens]`, prompt features shaped `[1, frames, 80]`, chooses `min(token_count, floor(frame_count/2))`, and returns contiguous prefixes `[1, P]` and `[1, 2P, 80]` (`request_builders.py:556-575`). With no reference, preparation creates `[1,0]` int32 prompt tokens and `[1,0,80]` prompt features. The speaker value is either a cloned reference embedding or an empty `[0,192]` tensor; the streaming normalizer later requires only rank two, not a fixed width (`request_builders.py:647-699`, `streaming.py:185-196`). The packed Flow adapter validates the actual speaker width against `spk_embed_affine_layer.in_features` when that attribute exists (`stages.py:101-131`).

At the vocoder, prompt normalization produces token `[1,P]` int32, feature `[1,F,80]`, and speaker `[1,S]` for rank-one inputs, with defaults `[1,0]`, `[1,0,80]`, and `[1,192]` (`streaming.py:157-196`). `_latch_prompts` pads nonzero `P` to the next multiple of 25. It repeats the last token for `pad` positions and the last feature frame for `2 * pad` positions. Empty tensors are unchanged because their computed pad is zero. The state then records the padded tensors, sets `prompt_pad=0`, and marks prompts latched (`streaming.py:39-46`, `streaming.py:110-154`, `models/fun_cosyvoice3/streaming_vocoder.py:492-524`).

Prompt data may arrive in either the terminal `StagePayload` or stream metadata. Payload latching deserializes `FunCosyVoice3State`; metadata latching runs only if at least one prompt key is present. If prompts were already latched, `_latch_prompts` normalizes/pads the new values and checks only the three tensor shapes against the existing state. It does not compare values and leaves the original tensors in place when shapes match (`models/fun_cosyvoice3/streaming_vocoder.py:137-176`, `models/fun_cosyvoice3/streaming_vocoder.py:508-524`).

`FunCosyVoice3State` serializes Flow prompt and audio tensors using `tensor_list`, which performs `detach().cpu().tolist()` on encoding and leaves list values as lists on decoding (`payload_types.py:13-31`, `pipeline_state.py:65-82`, `pipeline_state.py:100-121`, `pipeline_state.py:203-282`). Stream metadata from the first AR chunk bypasses that state serializer and carries the request-state tensor objects directly.

## Causal eligibility and 25/50/100 growth

For state offset `O`, current hop `H`, prompt pad `D`, and lookahead 3, the next non-final causal step requires `len(tokens) >= O + stream_hop_len(O,H,D) + 3`. At offset zero the hop is `H + max(D,0)`; later it is `H`. Since latching physically pads the prompt and resets `D=0`, the default reachable sequence is:

| Step | Offset before | Hop | Required cumulative generated tokens | New target mel frames | Offset after | Next hop |
|---|---:|---:|---:|---:|---:|---:|
| First | 0 | 25 | 28 | 50 | 25 | 50 |
| Second | 25 | 50 | 78 | 100 | 75 | 100 |
| Third | 75 | 100 | 178 | 200 | 175 | 100 |
| Later | 175, 275, ... | 100 | 278, 378, ... | 200 | +100 | 100 |

The producer sends cumulative totals 28, 53, 78, 103, 128, 153, 178, and so on. Consequently, after the first step the 50-token hop becomes eligible on the third producer message, and the first 100-token hop becomes eligible on the seventh. `next_stream_hop_len` doubles after every successful causal hop and clamps at 100. `disable_hop_growth=True` keeps the current hop unchanged (`streaming.py:49-94`, `models/fun_cosyvoice3/streaming_vocoder.py:130-135`, `models/fun_cosyvoice3/streaming_vocoder.py:556-618`).

Eligibility additionally requires latched prompts. Incoming code chunks are cast to long; shape `[N,1]` is flattened, any other non-rank-one shape is rejected, and the result is made contiguous. `ingest` calls `codes.tolist()` and extends a Python `list[int]`, another explicit device-to-host value materialization when the input is device-backed (`models/fun_cosyvoice3/streaming_vocoder.py:526-564`). No tokens are removed as hops advance; `token_offset` is the consumption cursor.

Non-final decoding advances exactly one causal hop. Final decoding repeatedly consumes every fully eligible causal hop, then always invokes one leftover Flow/HiFT call when any tokens exist. That leftover uses all tokens through `len(tokens)`, begins at the current offset, passes `streaming=False` and `finalize=True`, and concatenates any emitted pieces along the sample dimension. Even after the last full causal hop, its three lookahead tokens remain in the all-token final call (`models/fun_cosyvoice3/streaming_vocoder.py:698-795`).

## Streaming admission, waiting, and queue behavior

`StreamingSimpleScheduler` owns a thread-safe standard-library FIFO inbox and outbox, an internal deque for messages removed but deferred, and an `RLock` around request state. Its serving loop blocks on the inbox for at most 100 ms per poll and ignores messages for aborted IDs (`streaming_simple_scheduler.py:46-78`, `streaming_simple_scheduler.py:124-181`).

There are distinct admission policies:

- Buffered/non-streaming `new_request` batching uses `batch_compute_fn`, `max_batch_size`, and a deadline based on `max_batch_wait_ms`. It stops at streaming work or other message types, while an early done for a not-yet-seen payload is deferred and scanning continues. Optional request cost and `max_batch_cost` are enforced only in this path (`streaming_simple_scheduler.py:244-308`). For the configured vocoder, cost is total prompt-plus-target tokens times the Flow token/mel ratio, the cap is 8,000 frames, max batch is 16, and wait is 30 ms (`stages.py:1175-1181`, `stages.py:1292-1310`, `config.py:75-90`).
- CosyVoice streaming `new_request` collection does not block. If the first request is streaming, it takes already queued, distinct streaming payloads up to max batch size and stops at the first non-new, non-streaming, or duplicate-ID message, front-deferring that message (`models/fun_cosyvoice3/streaming_vocoder.py:193-228`).
- CosyVoice stream-chunk collection also does not block. It takes at most one chunk per request up to the cap, continues scanning past repeated chunks from an already selected request, and restores repeated chunks in original order ahead of the first non-chunk encountered (`models/fun_cosyvoice3/streaming_vocoder.py:255-287`).
- The CosyVoice peer wait is a separate fixed class value of 30 ms. At pump start, one ready first hop waits only if there is a not-ready offset-zero request that can join the sole ready shape key. An unlatch-ed first-hop peer is considered potentially joinable; a latched peer with another first-hop key is not. If no first hop is ready, a singleton ready follow-up may wait when there is a latched, not-ready follow-up with exactly the same `(hop_len, token_offset)`. Inbox messages arriving during the wait are ingested directly when they are stream chunks or streaming payloads; other messages are front-deferred and end the wait (`models/fun_cosyvoice3/streaming_vocoder.py:289-434`).
- Between causal steps, the pump drains already queued peer chunks/payloads without blocking. If exactly one first hop then becomes ready, it can enter the first-hop peer wait. The loop does not perform the analogous blocking follow-up wait between later steps (`models/fun_cosyvoice3/streaming_vocoder.py:436-490`).

Participant selection always gives ready first hops priority over follow-ups. First hops group by `hop + lookahead`; follow-ups group by `(hop_len, token_offset)`. The largest group is chosen and truncated to `_max_batch_size`; ties follow dictionary insertion/max traversal order. With coalescing or follow-up coalescing disabled, the first eligible request alone is returned. Streaming participant selection does not consult the buffered path's request cost or 8,000-frame cap (`models/fun_cosyvoice3/streaming_vocoder.py:566-602`).

The stage `StreamQueue` is per-request and unbounded; sender-side machinery owns backpressure. `put` and done/error signals use `put_nowait` and preserve queue order. Missing queues silently drop puts, including cleanup races. `get` consumes immediately if possible or awaits; done returns `None`, error raises. `close` removes the queue, records the ID in a capped closed set, and puts a done sentinel into the removed queue to wake existing waiters (`pipeline/stage/stream_queue.py:32-128`). The streaming scheduler's inbox/outbox queues are likewise unbounded `queue.Queue` instances (`streaming_simple_scheduler.py:46-78`).

## Causal Flow batch and CFG shape contract

For a selected group, the scheduler plan records one common hop, `token_end = token_offset + hop + 3`, the common offset, and whether batch size exceeds one. A singleton uses the external native Flow route through `token2wav_chunk`; two or more requests use `first_hop_batch` and the repository's packed Flow adapter (`models/fun_cosyvoice3/streaming_vocoder.py:604-696`).

The packed adapter validates each item as target tokens `[1,T]` with `T>0`, prompt tokens `[1,P]`, prompt features `[1,2P,output_size]`, and speaker embedding `[1,S]`. It left-aligns concatenated prompt and target tokens into int32 `[B,max(P+T)]`, constructs a boolean `[B,max_tokens,1]` token mask, pads prompt features into model dtype `[B,max_prompt_frames,output_size]`, and concatenates speaker embeddings into `[B,S]`. Length tensors are int64 on the Flow device (`stages.py:93-199`).

For causal inference, pre-lookahead removes three tokens per row before mel expansion. Mixed row lengths use row-specific body/context slices so shorter rows do not read right-padding. Hidden tokens are repeated by the token/mel ratio and transposed to `mu [B,C,F]`; masks are `[B,1,F]`; prompt mel values fill the corresponding prefix of `cond [B,C,F]`. Random noise is sliced from the decoder buffer, expanded to `[B,C,F]`, then cloned (`stages.py:202-248`, `stages.py:339-409`).

The Euler solver allocates its estimator inputs with a leading dimension `2B`: `x_in`, `mu_in`, and `cond_in` are `[2B,C,F]`; `mask_in` is `[2B,1,F]`; speaker input is `[2B,S]`. Both halves receive `x` and the mask. Only the first half receives `mu`, speaker conditioning, and prompt conditioning; the second half remains zero for those fields. The estimator output is split into first-half conditional and second-half unconditional tensors, then combined as `(1 + inference_cfg_rate) * conditional - inference_cfg_rate * unconditional` (`stages.py:251-298`). A PyTorch estimator receives the `streaming` flag; a non-module TRT wrapper uses `execute_flow_estimator` and does not receive it (`stages.py:434-453`). Default config leaves TRT disabled (`config.py:75-90`).

`inference_causal` generates with `streaming=True, finalize=False`, subtracts lookahead from target and combined token lengths, removes each row's prompt mel prefix, and returns `[1,output_size,(T-3)*2]` per request (`stages.py:511-532`). The scheduler then slices off `token_offset * 2` frames, leaving exactly the current hop's new 50/100/200 frames (`models/fun_cosyvoice3/streaming_vocoder.py:675-689`).

For a singleton, `token2wav_chunk` moves the all-generated prefix, prompt tensors, speaker embedding, and four int32 length tensors to the native Flow device, passes `streaming` and `finalize`, receives `(tts_mel, auxiliary)`, discards the auxiliary, and slices `offset * 2` mel frames before HiFT (`stages.py:1066-1114`). The exact native Flow internal masks, allocations, numerical path, and auxiliary result are owned by the external CosyVoice package and are unresolved by repository inspection.

## HiFT continuation state and host transfers

HiFT remains per request even after a batched Flow call. `_hift_delta` concatenates the prior `hift_mel` with the new mel along frame dimension 2, invokes external `HiFT.inference(speech_feat=..., finalize=...)`, and treats `speech_offset` as the number of already emitted samples in the newly returned cumulative speech tensor. It returns `tts_speech[:, held:]` after `detach().cpu()`, stores `tts_mel.detach()` as the next cumulative mel state, and sets the next offset to `tts_speech.shape[1]` (`stages.py:1131-1144`). Thus `hift_mel` remains on the mel computation device and grows cumulatively; every delta waveform crosses to CPU. The external HiFT implementation owns waveform overlap, receptive-field, and finalization mechanics beyond this visible cumulative interface.

In the batched Flow route, each returned mel is individually passed to `_hift_delta(..., finalize=False)` and its `hift_mel`/`speech_offset` are updated before the hop cursor grows (`models/fun_cosyvoice3/streaming_vocoder.py:675-696`). In the native singleton route, `token2wav_chunk` performs the same state transition and the scheduler stores both returned values (`models/fun_cosyvoice3/streaming_vocoder.py:757-795`). Final leftovers pass `finalize=True`; ordinary causal hops pass false.

The terminal stage serializes every waveform chunk by detaching, converting to float, moving to CPU, converting to NumPy float32, flattening to rank one, making it contiguous, and copying its bytes into `audio_waveform`; shape and dtype metadata plus sample rate and modality accompany it (`audio_payload.py:20-54`, `models/fun_cosyvoice3/streaming_vocoder.py:842-849`). `_hift_delta` has already moved its result to CPU, so the later `.cpu()` is normally a no-op at that boundary.

## Buffered route

Requests whose `request.params["stream"]` is false follow `_vocode_payload`/`_vocode_payloads` into `_CosyVoice3Vocoder.decode_payloads` (`models/fun_cosyvoice3/streaming_vocoder.py:117-124`). `BatchVocoderBase.decode_payloads` prepares every payload, invokes one batch decode, requires one result per input, and stores results in input order (`scheduling/vocoder_base.py:16-46`).

The concrete vocoder flattens serialized audio codes, constructs prompt/default tensors, computes total mel-frame cost, groups buffered Flow requests under its gap/padding policies, invokes `FunCosyVoice3Flow.inference` with `finalize=True`, groups mel outputs for HiFT padding, and writes each waveform back to its original index (`stages.py:939-1036`, `stages.py:1146-1242`). Buffered Flow returns all target-token mel frames rather than subtracting lookahead (`stages.py:493-509`). Buffered HiFT uses `finalize=True`; multi-item HiFT pads mels to the group maximum and trims each waveform to `original_mel_length * samples_per_frame` after one batch call (`stages.py:1183-1219`).

`store_result` clears state audio codes/samples, serializes waveform bytes, sets sample rate/modality, and includes usage when any usage field is nonzero (`stages.py:1221-1242`, `pipeline_state.py:294-304`).

If a streaming request reaches done without any prior audio emission and final incremental decode returns no waveform, `StreamingVocoderBase` calls model-specific `fallback_full_decode`. Fun-CosyVoice3 reconstructs codes and prompt tensors from the terminal payload and invokes `token2wav`, which is native Flow with `streaming=False, finalize=True`, no prior HiFT mel, and zero sample offset. Empty codes raise (`scheduling/streaming_vocoder.py:225-249`, `models/fun_cosyvoice3/streaming_vocoder.py:797-823`, `stages.py:1046-1064`).

## Terminal ordering, cancellation, and resource ownership

Done-before-payload is explicit. If `stream_done` arrives without `_stream_payloads[request_id]`, the scheduler records the ID in `_pending_done` and emits nothing. A later streaming payload is stored, prompts are latched, pending done is removed, and final handling runs immediately while holding the reentrant state lock (`streaming_simple_scheduler.py:470-519`). Stream chunks can independently create state before the payload; if the first chunk contains prompt metadata, causal work can start before terminal payload arrival (`scheduling/streaming_vocoder.py:257-334`).

At vocoder completion, the base runs the model's final decode, possibly fallback, appends a final stream chunk first when one exists, then appends a terminal `result` carrying a new `StagePayload`. Fun-CosyVoice3's terminal result data is metadata only: modality, sample rate, and optional usage. After the caller enqueues these messages in order, request state is cleared (`scheduling/streaming_vocoder.py:225-255`, `streaming_simple_scheduler.py:508-519`, `models/fun_cosyvoice3/streaming_vocoder.py:825-840`). The vocoder stage is terminal, so untargeted audio stream messages go to the coordinator and the result completes the request (`config.py:71-94`, `runtime.py:1171-1210`, `runtime.py:1655-1680`).

Abort records the ID, removes its payload and pending-done marker, and calls `clear_stream_state`; external abort callback cleanup runs outside the state lock on coalesced step failures. Aborted inbox messages are dropped. A failed coalesced Flow/HiFT step emits the same exception independently for every participant, clears every participant's state, and returns their IDs for external cleanup (`streaming_simple_scheduler.py:150-238`, `scheduling/streaming_vocoder.py:196-213`, `scheduling/streaming_vocoder.py:488-506`).

`clear_stream_state` removes emitted-state tracking, pops the request-local state, and calls `release_stream_resources`. Fun-CosyVoice3 clears the Python token list and drops `hift_mel`, prompt token, prompt feature, and speaker references; scalar cursors remain only on the now-unregistered state object (`scheduling/streaming_vocoder.py:251-276`, `models/fun_cosyvoice3/streaming_vocoder.py:851-859`). Normal completion records the request ID before clearing, so late chunks cannot recreate state. Completed IDs are compacted from above 10,000 down to 5,000 retained IDs. Abort IDs use the same 10,000/5,000 bounds (`scheduling/streaming_vocoder.py:287-299`, `streaming_simple_scheduler.py:187-209`).

Scheduler shutdown clears every registered stream state through the same release hook, logs and continues after individual release failures, clears emitted/completed registries, and then calls the session-level stop hook. Fun-CosyVoice3 defines no additional session resources in this subclass (`scheduling/streaming_vocoder.py:132-162`).

## Existing observability

Fun-CosyVoice3 logs every batched first hop at INFO with batch size and hop, and every batched follow-up with batch size, hop, and token offset (`models/fun_cosyvoice3/streaming_vocoder.py:662-674`). Coalesced-step failures and shutdown release failures log exceptions in the shared vocoder base; serving-loop, payload-validation, and abort-callback failures log in the simple scheduler (`scheduling/streaming_vocoder.py:145-162`, `scheduling/streaming_vocoder.py:488-506`, `streaming_simple_scheduler.py:124-145`, `streaming_simple_scheduler.py:228-238`).

The packed buffered Flow adapter optionally brackets its Euler solve with device events only when DEBUG logging is enabled; later logging queries the event and skips the record if it is still pending rather than synchronizing (`stages.py:301-336`, `stages.py:477-509`). Stage runtime emits first-stream and per-chunk events with target, chunk ID, modality, and transport around downstream routing (`runtime.py:1445-1535`). No request-visible causal hop/offset metadata is added to audio chunks by this scheduler.
