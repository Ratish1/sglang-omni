# Sector 15 — upstream runtime configuration resolution

## Scope and evidence boundary

This report traces the SGLang `ServerArgs` fields that own attention backend selection, KV page size and dtype, and CUDA-graph configuration through the resolution pipeline and publication. It describes the checked-out SGLang baseline only. “H100 Qwen2 default” below is a conditional static branch: CUDA device capability major 9, CUDA runtime at least 12.3, a model classified as non-MLA Qwen2, and otherwise-default inputs. The repository does not contain the effective remote checkpoint config, the serving command/config overlay, the detected device capability and capacity, installed optional packages, environment values, or a runtime `/server_info` capture. Those values therefore remain unresolved runtime evidence.

`runtime_context.py` and `model_executor/model_runner.py` were read completely in sector 11. Their publication and runner-local lines are cited here without duplicating those files in this sector's coverage manifest. `utils/common.py` was read completely for this sector. Its helper definitions establish that Hopper eligibility requires CUDA plus compute-capability major 9 and CUDA >=12.3 (`common.py:260-280`), that `is_no_spec_infer_or_topk_one` accepts no EAGLE top-k or top-k 1 with page size 1/`None` (`3611-3619`), and that device-memory capacity is returned in MiB (`815-840`).

## Ownership and call graph

`ServerArgs` construction preserves raw values; `__post_init__` performs no resolution (`server_args.py:3663-3671`). `resolve_once` calls `run_resolution_pipeline`, marks successful completion, refuses a second attempt after a failed partial pass, and treats an already-resolved record as a no-op (`3673-3706`). `runtime_context.publish` invokes this gate before installing the record (`runtime_context.py:1465-1512`).

The pipeline snapshots every dataclass field into `_raw_input`, preserves launcher-stage declarations, and then accumulates declarations in `_resolved_overrides` (`pipeline.py:50-63`). It parses CUDA-graph configuration before the platform and memory probes (`176-228`), applies model-specific declarations (`230-236`), resolves deterministic and ordinary attention (`238-253`), and finally fills an unset page size (`259-265`). Cache and model-capability validations continue later, then the pipeline marks the record finished (`341-370`).

Declarations do not normally mutate the dataclass. `resolution_result` walks the declaration stash in reverse, so the last declaration for a field wins, then falls back to `_raw_input` and the field (`overrides.py:157-178,269-287`). `resolution_projection` expands all dataclass fields from those effective values (`290-321`). `RuntimeContext.set_server_args` projects each `NS(...)` field into immutable-by-interface namespace bags from `resolution_result`; attention fields enter `exec.kernel`, graph fields enter `exec.graph`, page size enters `schedule`, and KV dtype enters `model` (`runtime_context.py:798-846,939-976`). Runtime reads use those bags. `attention_backends()` applies split-field fallback to `get_exec().kernel` (`1964-1978`). Post-publication `RuntimeContext.override` changes bag leaves and records provenance without changing the startup record (`1020-1063`); `resolved_server_args_dict` overlays those changes on `ServerArgs.resolved_dict()` (`1095-1123`). A later publish reprojects bags and discards the prior process-local override log (`1465-1500`).

The in-tree CUDA platform contributes no `ServerArgs` defaults: `CudaSRTPlatform` only reports FP8, decode graph, and piecewise graph support (`platforms/cuda.py:70-80`), while the base `apply_server_args_defaults` is a no-op (`platforms/interface.py:40-49`). Out-of-tree platforms can write directly; the pipeline captures those differences as declarations at `pipeline.py:215-221` and `overrides.py:219-266`.

## Default H100 Qwen2 attention resolution

All three raw attention fields default to `None`. The base field is `attention_backend`; `decode_attention_backend` and `prefill_attention_backend` explicitly have priority over it (`server_args.py:1657-1688`). `_attention_backend_default` first collapses equal, non-`None` prefill and decode choices into the base. Otherwise, only an unset base is auto-selected (`overrides.py:1111-1124`). The effective pair independently chooses each split field when truthy and otherwise falls back to the base (`model_override_base.py:164-178`). Thus an explicit split affects its phase, an explicit base supplies every phase lacking a split, and two equal explicit splits also publish that value as the base.

For a non-MLA architecture, `get_default_attn_backend` selects `fa3` when `is_hopper_with_cuda_12_3` is true and `is_no_spec_infer_or_topk_one` is true (`model_override_base.py:273-307`). The first predicate means CUDA, device-capability major 9, and CUDA >=12.3 (`utils/common.py:260-280`). The second is true when `speculative_eagle_topk is None`; with top-k 1 it additionally requires page size 1 or unset (`common.py:3611-3619`). Therefore an otherwise-default ordinary Qwen2 configuration on an H100 satisfying that CUDA gate publishes base `attention_backend="fa3"`, with both phase-specific fields still `None`; the effective prefill/decode pair is `("fa3", "fa3")`.

If that Hopper/CUDA predicate is false, the generic non-MLA fallback is `flashinfer` only when the published platform probe says FlashInfer is available and the model has no attention sinks; otherwise it is `triton` (`model_override_base.py:321-329`). The availability helper returns false when `SGLANG_IS_FLASHINFER_AVAILABLE` is false; otherwise it requires both an importable `flashinfer` module and CUDA (`common.py:361-368`). HIP and MPS have separate branches. This fallback is relevant to an H100 with an older CUDA build because “H100” alone does not satisfy the `fa3` condition.

Deterministic inference runs before ordinary attention resolution. When enabled with no explicit attention backend, Hopper and older architectures select `fa3`; Blackwell selects another branch (`overrides.py:1077-1107`, `attention_hook.py:515-634`). The ordinary default then observes the existing declaration. The Qwen2 architecture has no exact or predicate-specific attention override in the checked-in override registry; registry order is constants, exact providers, then predicate providers, all last-writer-wins (`overrides.py:412-448`). A remote-code checkpoint exposing another architecture or model capabilities can take a different registered/model-specific path.

`handle_attention_backend_compatibility` owns this sequence: default fill, graph changes for torch-native/flex, MLA page and dtype constraints, split TRT-LLM validation, FA3 FP8-E5M2 fallback, FA4 constraints, platform fallbacks, and dual-chunk handling (`attention_hook.py:43-228`). For the conditional default above, none of those later branches changes `fa3` when KV dtype remains `auto`.

## KV page size and dtype

Raw `page_size` is an optional resolvable field defaulting to `None` (`server_args.py:808-812`). After attention resolution, `_page_size_default` preserves any non-`None` value, uses 64 only for a HIP vectorized-5D AITER layout or MUSA, and otherwise declares 1 (`overrides.py:1377-1399`). FA3 has no page-size snap in the compatibility handler. Consequently the conditional ordinary Qwen2/H100 default publishes `page_size=1`. An explicit page size wins this default pass. Backend-specific compatibility declarations can still force supported values before the default: for example TRT-LLM MHA accepts 16/32/64/128 and converts any other value, including an unset value at that earlier slot, to 64 (`1128-1204`).

Raw `kv_cache_dtype` is resolvable and defaults to the string `"auto"` (`server_args.py:592-618`). The DSA and DeepSeek-V4 passes can replace `auto`, but their architecture gates do not apply to ordinary Qwen2 (`overrides.py:599-643,907-928`). The cache hooks validate explicit MXFP8/FP4 and special pool modes; they do not replace ordinary Qwen2 `auto` (`kv_cache_hook.py:24-468`). The published `model.kv_cache_dtype` therefore remains `"auto"` under the conditional default.

Runner initialization separately interprets that string. `configure_kv_cache_dtype` uses checkpoint `quant_config.kv_cache_quant_algo == "FP8"` to choose an FP8 torch dtype and a concrete backend tag; otherwise `auto` chooses the model dtype (`mem_cache/kv_cache_dtype.py:22-47`). Explicit strings map to their torch dtypes or validation errors (`48-81`). `ModelRunner.configure_kv_cache_dtype` stores the concrete torch dtype on the runner and keeps either the returned concrete tag or the published string as `kv_cache_dtype_str` (`model_runner.py:1381-1406`). This runner-local operation does not rewrite the published `ServerArgs`/bag value.

## CUDA-graph defaults and H100 capacity sizing

The raw structured graph field and every per-phase convenience selector default to `None`; phase-disable booleans default false (`server_args.py:1851-1910`). A default `CudaGraphConfig` has decode backend `full`, prefill backend `breakable` on CUDA and `tc_piecewise` elsewhere, and both phases initially have `max_bs=None`, `bs=None`, and `tc_compiler="eager"` (`model_executor/cuda_graph_config.py:32-47,90-121,143-190`).

`parse_cuda_graph_config` applies sources in increasing authority: defaults, legacy global disable, phase-disable booleans, convenience fields, then explicit JSON. Each non-default `(phase,key)` is recorded in `_cuda_graph_config_locked` (`cuda_graph_hook.py:37-103`). Explicit JSON therefore wins over convenience and legacy values for the same key. Compatibility skips its automatic prefill policy when the prefill backend key is locked (`106-166`). With ordinary text Qwen2, PP size 1, and default features, CUDA leaves prefill `breakable` and decode `full`. PP>1 disables the default breakable prefill backend unless it was explicitly selected (`118-134`); multimodal and other listed compatibility conditions can also change it (`136-323`). Disaggregation roles disable the phase they do not serve unless that phase backend was locked (`569-588`).

The memory handler then fills missing graph dimensions. Its input is device memory capacity in MiB. CUDA capacity first comes from the minimum parseable `memory.total` returned by `nvidia-smi` across visible GPUs; missing/failed/unparseable output falls back to the minimum total returned by `torch.cuda.mem_get_info` across visible CUDA devices (`common.py:620-688,815-840`). For 60–90 GiB, the branch labelled “H100, A100” sets an unset `chunked_prefill_size` to 8,192 and an unset decode `max_bs` to 256 for TP<4 or 512 for TP>=4 (`memory_hook.py:102-115`). The 90–160 GiB branch uses the same values (`116-129`). Therefore the same sizes result for an unpartitioned H100 capacity landing in either range; a MIG partition or another reported capacity can select another capacity branch. If capacity is unavailable, fallback values are chunk 4,096 and decode maximum 160 (`141-150`).

When decode `bs` is absent, normal non-speculative buckets are `[1,2,4,8,12]`, multiples of 8 from 16 through 256, multiples of 16 from 272 below 512, and multiples of 32 from 512 through `max_bs`, filtered to the maximum; the maximum is appended when absent (`cuda_graph_hook.py:512-544`). For the TP<4 H100 default, only the first two portions through 256 remain. If decode `bs` was explicitly supplied, `max_bs` is reset to `max(bs)` (`memory_hook.py:152-160`).

For non-MLA Qwen2, an unset prefill `max_bs` becomes `chunked_prefill_size`, hence 8,192 in the two H100-capacity branches; `max_total_tokens`, when explicit, caps it (`memory_hook.py:185-217`). An absent prefill bucket list is generated from the staged ranges at `cuda_graph_hook.py:492-509`; with maximum 8,192 this includes every generated value through 8,192. Explicit `max_bs` or `bs` values already folded from structured/convenience input are preserved according to the handler's per-field checks.

The resulting conditional default published graph object is therefore:

| Phase | Backend | `max_bs` | `bs` ownership |
|---|---|---:|---|
| decode | `full` | 256 when TP<4; 512 when TP>=4 | generated by `generate_decode_cuda_graph_batch_sizes` unless explicit |
| prefill | `breakable` | 8,192 | generated by `generate_prefill_cuda_graph_batch_sizes` unless explicit |

These are published configuration values, not proof that every forward uses a graph. In the CosyVoice runner examined in sector 11, custom prefill explicitly reports `can_run_cuda_graph=False`; that execution fact coexists with a published prefill graph configuration. The effective launch overlay can also supply graph values before resolution, and runtime code can override bag leaves after publication.

The concrete Omni CosyVoice launch supplies such an overlay before upstream resolution. `FunCosyVoice3EngineBuilder.generation_defaults` sets legacy `cuda_graph_max_bs=32`, leaves global graphs enabled, and does not opt into a prefill backend (`sglang_omni/models/fun_cosyvoice3/engine_builder.py:60-77`, fully covered in sector 05). The shared Omni `build_sglang_server_args` translates that legacy key to `cuda_graph_max_bs_decode`, sets an absent prefill backend to `disabled`, constructs `ServerArgs`, and calls `resolve_once` (`sglang_omni/scheduling/sglang_backend/server_args_builder.py:13-36,67-103`, fully covered in sector 05). Upstream graph parsing therefore locks decode `max_bs=32` and prefill backend `disabled` before the capacity handler. The capacity branch does not replace the already-populated decode maximum, and Omni's shared policy supplies decode buckets `[1,2,4,8,12,16,24,32]` (`generation_batch_policy.py:42-54`, fully covered in sector 05). The generic H100 256/512 row above is consequently an upstream no-override default, not the CosyVoice decode configuration. The disabled prefill phase does not construct a prefill graph runner even though upstream sizing can still fill that phase object's otherwise-unset `max_bs`/`bs` fields.

## Override authority summary

1. Constructor/CLI/config values form `_raw_input`. Launcher-stage declarations are retained.
2. Resolver declarations overlay raw input in pipeline order; the last declaration for a field wins. An in-tree CUDA platform adds no direct defaults.
3. Attention split fields have per-phase authority over the common attention field. Ordinary Qwen2 has no checked-in architecture-specific replacement.
4. Graph-source precedence inside parsing is explicit JSON, convenience fields, legacy flags, defaults. Later compatibility/model declarations can replace graph fields under their stated conditions; the default Qwen2/FA3 path does not.
5. Publication snapshots resolved values into namespace bags. Post-publication `RuntimeContext.override` changes those bags and is visible in resolved internal-state serialization. Re-publication reconstructs bags from the record's resolution and drops process-local overrides.
6. KV `"auto"` remains the published value for ordinary Qwen2; a runner subsequently derives its concrete allocation dtype from model/checkpoint state.

## Existing observability and unresolved runtime evidence

Resolution logs the auto-selected attention backend (`overrides.py:1116-1123`) and compatibility fallbacks. Graph compatibility and H100 memory sizing emit selected warnings/info only on their respective branches (`cuda_graph_hook.py:106-476`; `memory_hook.py:26-289`). `ServerArgs.resolved_dict()` is the resolved startup serialization (`server_args.py:3708-3719`), while the runtime context serialization additionally includes post-publish overrides (`runtime_context.py:1095-1123`). These interfaces can expose effective values, but no output from them was supplied for the target deployment.

Unresolved external/runtime inputs are: actual `CosyVoice-BlankEN/config.json` architecture and attention traits; model dtype and checkpoint KV quantization metadata; exact GPU capability, CUDA runtime, total/partitioned memory and TP size; FlashInfer availability; speculative settings; JSON/convenience/legacy graph inputs; page/KV overrides; environment gates; disaggregation/PP roles; and post-publication overrides. No claim here identifies the backend, page size, concrete KV allocation dtype, or graph buckets of an actual remote run.
