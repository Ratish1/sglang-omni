# Sector 16 — reached FlashAttention v3 backend

## Scope and source identity

This report closes the SGLang v0.5.19 FA3 owner selected by the sector-15 conditional default: ordinary non-MLA Qwen2 on H100 (SM90), CUDA >= 12.3, no attention override, and no speculative setting that defeats that selection. The SGLang source is commit `0bcd822377da7b5718e674eaf9c870d349424dd1` (tag `v0.5.19`). The primary backend owner is `python/sglang/srt/layers/attention/flashattention_backend.py:1-3709`; the registry creates it with the default `fa_impl_ver=3` for `fa3` (`attention_registry.py:216-238`).

The report covers the backend's complete implementation, its version-dispatch wrappers, and the complete KV-index translator/read-table owners. Other supported modes in those full files are identified but are not attributed to the ordinary CosyVoice route. The actual FlashAttention CUDA/C++ implementation is external: the default Python path imports it from the installed `sgl_kernel.flash_attn`. No installed module, wheel payload, runtime version, or external FlashAttention source revision was inspected or inferred.

## Reached call graph and phase split

The previously closed routing is `Qwen2Attention.forward` -> `RadixAttention.forward` -> `AttentionBackend.forward` -> `FlashAttentionBackend.forward_extend` or `forward_decode`. Qwen2 is decoder-only MHA/GQA: it passes Q/K/V, TP-local head geometry, `head_dim**-0.5` scaling, and a `ForwardBatch`; it does not set cross-attention, sliding-window, sink, custom-mask, score-modifier, or MLA arguments (`qwen2.py:126-213`; `radix_attention.py:98-175`). `AttentionBackend.forward` sends decode mode to `forward_decode`, idle to an empty result, and other non-NPU modes, including prefill/extend, to `forward_extend` (`base_attn_backend.py:249-291`).

For the CosyVoice runner, prefill remains the custom eager path already established in sector 11: its runner reports prefill graph admission false and executes the Qwen backbone through the normal attention call. Decode is eligible for SGLang's full decode CUDA graphs. Thus the reached FA3 phase behavior is:

1. Eager custom prefill calls `init_forward_metadata`, then each Qwen layer calls `forward_extend`.
2. Decode graph initialization calls `init_cuda_graph_state`; capture/replay metadata work runs through `init_forward_metadata_out_graph`; the layer calls to `forward_decode` are captured against address-stable metadata and output buffers.

The backend advertises full-graph support for decode, idle, target verification, and draft extend, and states that ordinary extend/draft extend are not supported by its legacy decode-graph contract (`flashattention_backend.py:126-149`). The same full owner now also contains a separate full-prefill-CUDA-graph metadata branch (`469-703`). That supported upstream mode does not change the CosyVoice runner's explicit eager-prefill admission result.

## Backend construction and FA3 implementation dispatch

`FlashAttentionBackend.__init__` retains strong references to the request-to-token pool, token-to-KV pool, its `req_to_token` tensor, and the runner's `KVIndexTranslator`; records context length, page size, cache dtype, model/head geometry, and optional speculative/local/SWA state; and initializes per-forward and per-graph metadata holders (`151-374`). For `fa_impl_ver == 3`, it imports `flash_attn_varlen_func`, `flash_attn_with_kvcache`, and `get_scheduler_metadata` from `sgl_kernel.flash_attn`; it stores the first two on the instance and the scheduler function as `_get_scheduler_metadata` (`280-331`). The layer forward methods invoke the module-level `sglang.kernels.ops.attention.flash_attention` wrappers with `ver=3`, and those wrappers forward to `flash_attention_v3.py` (`flash_attention.py:9-327`).

FA3 support in that wrapper means MUSA capability >=3, or CUDA >=12.3 with compute-capability major 8 or 9 (`flash_attention_v3.py:84-98`). On the stated H100 gate, both paged-KV and varlen entry points therefore use FA3. `SGLANG_USE_SGL_FA3_KERNEL` defaults to true (`environ.py:1156`), so `_load_fa3_kernels` normally loads the two functions from `sgl_kernel.flash_attn`; `cache_once` memoizes the selected function dictionary for each argument tuple (`flash_attention_v3.py:31-80`; `jit/utils/common.py:27-41`). If that environment value is false, the wrapper instead attempts `kernels-community/sgl-flash-attn3` revision `v1`, loading from `SGLANG_CACHE_DIR/kernels.lock` when present or through the `kernels` package otherwise; any exception logs a warning and falls back to `sgl_kernel` (`flash_attention_v3.py:11-80`). This alternate implementation-loading branch is supported but is outside the stated default.

`flash_attn_with_kvcache` rejects an unsupported device, requires last-dimension-contiguous K cache when present and V cache always, and forwards all metadata, scale, mask/window, split, LSE, sink, and optional-output arguments to the loaded external function (`102-184`). `flash_attn_varlen_func` forwards the corresponding unpaged/varlen contract on supported FA3 hardware; only unsupported hardware falls back to the external `flash_attn` package's FA2 functions (`188-280`). `_call_fa3_kernel` passes `out=` when supplied and retries without it only when the callee raises the specific unexpected-keyword `TypeError` (`19-27`).

## Eager prefill metadata, layout, and mask

`init_forward_metadata` creates a fresh `FlashAttentionMetadata` for an eager forward (`flashattention_backend.py:705-1191`). In ordinary extend it converts batch sequence lengths to int32, builds cumulative K lengths, and slices `req_to_token[req_pool_indices, :max_seq_len_k]` into a page table. `max_seq_len_k` uses the published CPU mirror when present and otherwise the static context limit; query cumulative lengths come from `extend_seq_lens`. Prefix-bearing batches use distinct Q and K cumulative arrays, while a no-prefix batch aliases `cu_seqlens_q` to `cu_seqlens_k` (`1002-1067`). With the conditional sector-15 default `page_size=1`, the later page-striding conversion is skipped (`1140-1189`), so table entries remain per-token KV slot identities.

For the ordinary non-unified pool, `KVIndexTranslator.index_table_for_batch` returns the original two-dimensional `req_to_token` tensor and the original request-row tensor without allocation, copy, or translation (`kv_index_translator.py:181-206,281-311`). `init_forward_metadata` therefore keeps its already sliced page table. Unified-memory translation is a separate supported mode described below.

Each Qwen layer's `forward_extend` first writes supplied K/V into the persistent per-layer KV pool when `save_kv_cache` is true (`flashattention_backend.py:1248-1331`). It then selects causal decoder attention, `window_size=(-1,-1)`, and no cascade, cross-attention, local-attention, SWA, score-modifier, sink, or relative-bias branch for ordinary Qwen2 (`1333-1383`). `prepare_paged_mha_query` leaves Q at model dtype for `kv_cache_dtype_str == "auto"`; explicit non-auto cache formats can cast Q and expand scalar K/V descales (`1215-1246`).

The K/V buffers are viewed as `[num_pages, page_size, tp_kv_heads, head_dim]`. Q is made contiguous and viewed as `[tokens, tp_q_heads, head_dim]`. The paged call passes the int32 page table, per-request cache lengths, cumulative Q and K lengths, maximum query length, QK scaling, `causal=True`, no window, the layer logit cap, `num_splits`, `ver=3`, and an optional graph/output buffer (`1193-1213,1453-1583`). The wrapper documents bottom-right causal alignment for unequal Q/K lengths; with ordinary autoregressive extend, that exposes each query to its cached prefix and preceding/current extend tokens (`flash_attention.py:75-105`). The result is flattened to `[tokens, tp_q_heads * v_head_dim]` (`flashattention_backend.py:1822`).

The ordinary eager path reads Python/CPU metadata such as `extend_prefix_lens_cpu` and maximum extend length. Where a live CPU sequence-length mirror exists, those reads do not require device-to-host transfer. A missing mirror widens `max_seq_len_k` to `max_context_len`; local attention, cross-attention, prefill-aware SWA, and some speculative branches contain explicit `.cpu()`/`.item()` boundaries, but those modes are not reached by ordinary Qwen2.

## Decode execution and CUDA-graph state

Ordinary eager decode metadata converts sequence lengths to int32, creates unit-stride cumulative Q positions, cumulative K lengths, and a request-row page-table slice, then optionally precomputes FA3 scheduler metadata (`flashattention_backend.py:807-850`). `_compute_scheduler_metadata` returns none for MLA or when distributed attention disables precomputation; otherwise it calls external `sgl_kernel.flash_attn.get_scheduler_metadata` with batch/head/page geometry, causal mode, cache lengths, and `num_splits` (`376-403`). With deterministic inference disabled, FA3 sets `num_splits=0`, delegating split selection to the external runtime; deterministic mode sets it to 1 (`346-361`).

`forward_decode` writes current K/V before attention, selects the same paged cache layout, makes Q contiguous as `[tokens, tp_q_heads, head_dim]`, and for ordinary self-attention calls the versioned paged-KV wrapper with the page table, cache lengths, unit Q cumulative lengths, causal mode, layer scale/cap, scheduler metadata when applicable, and the optional preallocated output (`1824-2087`). It returns the same flattened head layout (`2167`). No custom tree mask is passed in normal decode; visibility is set by each row's page table and `cache_seqlens` plus causal alignment.

`init_cuda_graph_state(max_bs, max_num_tokens)` allocates persistent device tensors for cache lengths `[max_bs]`, Q/K cumulative lengths `[max_bs+1]`, and an int32 page table `[max_bs,max_num_pages]`; it also allocates `1 + round_up(max_bs,4)*4` int32 scheduler words when FA3 scheduler precomputation applies (`2169-2233`). Ordinary Qwen2 does not allocate the file's conditional local, SWA, encoder, or speculative graph buffers. `_bind_metadata_buffers` constructs metadata objects whose fields are slices/views of these tensors and stores the ordinary decode object by captured batch size (`2492-2711`). These backend-owned tensors and metadata survive across graph replays, so captured kernel arguments retain stable addresses.

During capture, `_init_full_cg_decode_metadata` binds the buffers and applies capture metadata. During replay it calls the same `_apply_cuda_graph_metadata` body against the already bound object (`485-599,2727-3146`). Ordinary decode asks the translator for an index-table view and calls `normal_decode_set_metadata`, which uses the page-size-one/no-SWA Triton specialization under the stated defaults. One program computes `cache_seqlens = seq_lens + delta` and the cumulative K array; the two-dimensional batch/column grid gathers only each row's live page-table prefix in 256-column blocks. Stale tail columns remain but are outside `cache_seqlens` (`metadata.py:294-359,572-757`). Because `needs_cpu_seq_lens=False`, replay passes no CPU mirror into this method and uses `max_context_len` only for the scheduler split heuristic; it does not call `.cpu()`, `.item()`, or `.tolist()` in the ordinary replay branch (`flashattention_backend.py:2870-2937`). The scheduler result, when enabled, is copied into the preallocated scheduler buffer rather than rebinding it (`2939-2955`).

Capture preparation itself materializes `seq_lens.cpu()` before applying the initial graph metadata (`flashattention_backend.py:519-530`). This is an outside-graph device-to-host boundary during capture setup. The normal replay branch described above does not repeat it.

The backend returns sequence-length fill value 1 for padded graph lanes (`3148-3150`). The graph runner owns bucket padding and replay orchestration; this backend owns the stable attention metadata and page-table contents. An optional `ForwardBatch._attn_output` is viewed rather than allocated in both extend and decode (`flashattention_backend.py:1417-1421,1908-1912`), preserving an output address suitable for capture.

## KV index translation contract

`KVIndexTranslator` is constructed once per model runner (`kv_index_translator.py:96-153`). Its three namespaces are virtual IDs stored in `req_to_token`, current physical pool IDs, and kernel-facing IDs. All coincide for a plain pool. Translation activates only when the allocator is `UnifiedMambaTokenToKVPoolAllocator` or `UnifiedSWATokenToKVPoolAllocator` and its cache object is the runner's token-to-KV pool (`99-153`). That unified-memory mode is supported code in the reached backend owner, but it is not part of the otherwise-default Qwen2 conditions stated for this report.

For translation, `make_capture_tables` creates zero-filled, capture-stable int32 `[max_bs,max_pages]` full and optional SWA tables; zero is the reserved padding identity (`155-177`). `build_index_table` either returns the plain aliases or fills caller-owned graph tables/fresh eager tables using `build_kv_read_table`, then returns row IDs local to the compact batch and marks the table translated (`181-259`). `index_table_for_batch` memoizes one eager table by weak `ForwardBatch` identity, while captured replay explicitly rebuilds into owned fixed buffers (`281-311`). `rebind_write_loc` replaces the forward batch's full-side output locations with a fresh translated tensor so scheduler-owned virtual locations remain unchanged (`331-343`). SWA translation and backend boot guards occupy `313-376` and are unrelated to ordinary Qwen2.

The Triton read-table kernel launches a two-dimensional `(batch, ceil(max_pages/256))` grid. For each live request page it gathers the virtual page-start token from `req_to_token`, maps negative IDs to zero, gathers the virtual-to-physical page, multiplies into the kernel-facing page namespace, clamps negative/freed mappings to zero, and writes int32 entries. It writes only `ceil(seq_len/page_size)` live columns; captured table tails retain prior values, while attention is bounded by `cache_seqlens` (`kv_read_table.py:1-77`). The Python owner checks packed int32 output capacity and source width and has an equivalent Torch CPU branch; CUDA enqueues the Triton kernel without an explicit synchronization (`80-140`).

## Streams, synchronization, and lifetime

The reached backend contains no private CUDA stream or event for ordinary FA3 MHA. KV writes, metadata kernels, wrapper calls, and output writes are issued through PyTorch/Triton on the active execution stream; the Python files do not insert a stream synchronize. Exact stream use and launch behavior inside installed `sgl_kernel.flash_attn` remain external evidence. The explicit `rel_bias_event.wait()` joins an alternate producer stream only for FA4 relative bias and is excluded from FA3 (`flashattention_backend.py:1395-1415,1885-1906`).

Backend lifetime is runner lifetime: it holds the pools, translator, graph dictionaries, and fixed device buffers. Eager `FlashAttentionMetadata` is recreated per forward and reused by all layers within that forward. Graph metadata objects and their backing tensors are created at graph setup/capture and reused in place on replay. Per-layer K/V storage is persistent in the token-to-KV pool; the backend writes new K/V before issuing attention on the same Python execution path.

The ordinary graph replay metadata route avoids an explicit host synchronization. The surrounding CosyVoice generation still has the already documented post-sampling `token_ids.tolist()` device-to-host boundary; that is outside this attention backend. Optional local-attention metadata converts CUDA tensors to CPU/NumPy, and encoder/speculative branches contain `.item()` calls, but they are excluded supported modes here.

## Backend variants and excluded supported modes

The complete owner also implements FA4, MLA/absorbed MLA, context parallelism, cross attention, encoder-only/bidirectional attention, local/chunked virtual batches, sliding-window and prefill-aware SWA, embedding-mode KV bypass, target-verify cascade merging, multi-step speculative draft backends, and full prefill CUDA-graph metadata. The registry's `fa4`, dual-chunk, MUSA, MiniCPM, XPU, FlashInfer, and Triton factories select different implementations or wrappers. None is part of the stated ordinary Qwen2/H100 `fa3` route.

FA3 and FA4 share `FlashAttentionBackend`, but `fa_impl_ver` separates their implementation loading and capabilities. FA4 alone accepts score modifiers, sheared relative bias, MXFP8 scale-factor layout, runtime policy, and its alternate kernel modules (`flashattention_backend.py:280-345,405-425,1268-1270,1384-1415`). FA3 alone uses `sgl_kernel.flash_attn.get_scheduler_metadata`. This report does not merge these version-specific contracts.

## Existing observability

The FA3 loader emits a debug record when the default `sgl_kernel` implementation is selected and a warning containing the repository/lockfile and exception when community-kernel loading fails (`flash_attention_v3.py:31-68`). Both public FA3 wrappers carry `debug_kernel_api` (`102,188`). Kernel API logging defaults off; when enabled, levels >=3 serialize arguments/results for logs, level >=5 computes tensor statistics with `.item()` outside graph capture, and level >=10 dumps tensors unless capture is active (`kernel_api_logging.py:54-90,134-176,402-472`). Those optional modes can introduce host reads and file I/O; no evidence says they were enabled.

## Facts and unresolved evidence

Under the conditional sector-15 defaults, the registered implementation is FA3 for both phases, page size is 1, published KV cache dtype is `auto`, custom CosyVoice prefill remains eager, and normal decode can be captured by the full decode graph. In ordinary Qwen2, the backend uses causal paged MHA, writes K/V before attention, uses no custom mask or window, and refreshes fixed decode metadata outside the captured graph without an explicit host read.

Unresolved external/runtime evidence is the actual checkpoint model/head dimensions and dtype, concrete runner KV dtype derived from checkpoint quantization, batch and sequence lengths, TP size, graph bucket/admission result for a live decode, environment overrides, unified-memory enablement, and active logging. The installed `sglang-kernel` artifact and its `sgl_kernel.flash_attn` CUDA/C++ implementation were not inspected. The in-tree package pin and CUDA startup check expect distribution version `0.4.6.post1`, but they do not establish the live imported file, build flags, kernel variant, numerical identity, launch geometry, workspace use, or measured stream timing.
