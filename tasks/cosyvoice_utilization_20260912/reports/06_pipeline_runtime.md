## Default Fun-CosyVoice3 topology

`FunCosyVoice3PipelineConfig` declares, in order, `preprocessing`, `tts_engine`, and `vocoder`. Every stage has `process="pipeline"`; every stage has the default `tp_size=1`; `preprocessing` is CPU-unplaced, while `tts_engine` and `vocoder` both have `gpu=0`. The config declares no `processes` entry, so `_DEFAULT_PROCESS_CONFIG` supplies one replica. The entry stage defaults to the first stage, `preprocessing`; `vocoder` is the sole terminal stage. Sources: `models/fun_cosyvoice3/config.py:32-96`, `config/schema.py:714-721`, `config/topology.py:101-166`.

The process string is resolved rather than counted directly. `compile_logical_processes` groups all three stages into one `LogicalProcess(name="pipeline", stage_names=("preprocessing", "tts_engine", "vocoder"), tp_size=1, num_replicas=1)`. Replica expansion leaves names and membership unchanged. Placement records two GPU stages on GPU 0. `build_process_topology_plan` then produces exactly one non-TP `ProcessGroupPlacement`, named `pipeline`, containing all three stages and resolving its group GPU to 0. `_build_stage_groups` converts that group into one `StageWorkerProcessSpec` containing three `StageLaunchConfig` objects in declaration order. `StageGroup.spawn` calls `spawn` once for that spec and `_process_name` labels the child `process-pipeline`. Sources: `config/topology.py:101-166,255-315,340-368`; `pipeline/replicas.py:109-186`; `pipeline/mp_runner.py:83-233`; `pipeline/stage_workers.py:272-309,963-971`.

Thus the default serving topology established by code is:

| Runtime owner | Default Fun-CosyVoice3 instance |
|---|---|
| Launcher/coordinator process | Owns `MultiProcessPipelineRunner`, `Coordinator`, completion loop task, and child monitor task on its asyncio loop. |
| Spawned worker processes | One daemon spawn child, logical process `pipeline`, hosting all three stages. |
| Worker asyncio loops | One loop created by `asyncio.run(_start_and_run())`, shared by all three `Stage.run()` coroutines, their abort listeners, outbox drain tasks, and receive tasks. |
| Scheduler threads | Three daemon threads: `scheduler-preprocessing`, `scheduler-tts_engine`, and `scheduler-vocoder`. Each calls its scheduler's blocking `start()`. |
| Preprocessing compute workers | Its `SimpleScheduler(max_concurrency=8)` creates an event loop inside the preprocessing scheduler thread, one bridge coroutine and eight worker coroutines. Each worker dispatches the synchronous preprocessing function through `asyncio.to_thread`; the loop's default executor owns the actual compute calls. |
| TTS scheduling | One `OmniScheduler` loop in `scheduler-tts_engine`. Fun-CosyVoice3 defaults leave Omni async decode and overlap disabled, so `start()` selects its normal event loop. Request-builder workers default to one, so no request-build `ThreadPoolExecutor` is created by that default. |
| Vocoder scheduling | One `FunCosyVoice3StreamingVocoderScheduler`/`StreamingSimpleScheduler` blocking loop in `scheduler-vocoder`; its model decode calls execute in that scheduler thread. |

Sources: `pipeline/mp_runner.py:522-680,721-745`; `pipeline/stage_workers.py:456-517,622-810`; `pipeline/stage/runtime.py:204-250,320-373`; `scheduling/simple_scheduler.py:25-327`; `scheduling/streaming_simple_scheduler.py:34-551`; `models/fun_cosyvoice3/engine_builder.py:18-143`; `scheduling/engine_factory.py:42-236,326-519`; inspected boundary `scheduling/omni_scheduler.py:167-430,1770-1816`.

All stages in the worker share one interpreter, module globals, heap, torch CUDA context, and process-wide torch caching allocator. `LocalStageDispatcher` passes Python object references directly and documents receiver read-only ownership unless projection produced an isolated object. The three stage schedulers communicate with the worker loop through thread-safe standard-library queues (`inbox`/`outbox`). Sources: `pipeline/local_dispatch.py:9-88`; `pipeline/stage/runtime.py:1092-1169`; scheduler constructors cited above.

## Startup, readiness, and construction order

`MultiProcessPipelineRunner.start` uses multiprocessing `spawn`, prepares topology/endpoints, validates declared GPU capacity, builds groups, starts the coordinator and completion loop, starts optional MPS/weight-sharing resources, then spawns groups by startup waves. With default CosyVoice config, `mps="off"` and `weight_share="off"`, so there is one wave containing the one group. The runner awaits every group's ready event before registering stage control endpoints and setting `_started=True`. A ready wait checks both timeout and premature process death. Sources: `config/schema.py:580-637`; `pipeline/mp_runner.py:522-680`; `pipeline/stage_workers.py:311-350`.

Inside the worker, accelerator environment preparation runs for all three specs before scheduler construction. The stages are then constructed serially in config order. `_construct_scheduler` imports each factory in the child; for a GPU stage it sets the current device, applies any total-reserve allocator cap, acquires the per-GPU startup lock, and invokes the factory. Consequently TTS engine construction completes before vocoder construction begins. The process-local dispatcher is registered only after all stage objects have been constructed. Sources: `pipeline/stage_workers.py:406-517,622-810,818-947`.

`_start_and_run` starts all stages sequentially. Each `Stage.start` starts its control plane and comm engine, captures the worker asyncio loop, marks itself running, then starts its scheduler thread. It does not await scheduler initialization after starting the thread. After all three `Stage.start` calls return, the worker sets the process ready event, creates one `Stage.run` task per stage, and gathers them. A stage's second `start` call from `run` returns because it is already running. Therefore worker readiness means factories completed and stage control/comm planes and scheduler threads were started; it does not include an explicit scheduler-thread readiness acknowledgment. Sources: `pipeline/stage_workers.py:456-517`; `pipeline/stage/runtime.py:204-250,320-373`.

Any gathered stage failure tears down all stages in the process; the child exits, and the runner's five-second child monitor calls coordinator fail-all and stops the runtime when MPS is off. There is no per-stage process isolation in this default grouping. Sources: `pipeline/stage_workers.py:456-619`; `pipeline/mp_runner.py:721-758`.

## Configuration resolution and memory ownership

`PipelineConfig` validates unique names, exactly one of `next` or `terminal`, referenced stages, process declarations for non-TP stages, TP exclusivity, and the reserved replica suffix. `FunCosyVoice3PipelineConfig.process_local_edges` additionally requires `preprocessing -> tts_engine` to remain within one process. Process compilation is the final membership decision; expanded topology does not regroup by stage name. Sources: `config/schema.py:320-489,580-948`; `models/fun_cosyvoice3/config.py:32-106`; `config/topology.py:101-252`.

Typed `factory.*` values override code-level factory kwargs after checking the imported factory signature. `engine.*` set values become `server_args_overrides`. Standard `model_path`, `gpu_id`, optional configured `total_gpu_memory_fraction`, and `max_audio_clip_s` are injected only where the factory signature declares them. In the default config, both GPU factories receive `gpu_id=0`; no stage declares `gpu_memory_fraction`, `total_reserve_bytes`, or `engine.kv_cache_bytes`. Sources: `config/runtime.py:45-244`; `models/fun_cosyvoice3/config.py:49-96`.

Placement sees `tts_engine` and `vocoder` on GPU 0, but GPU colocation validation counts OS process names: both belong to the same `pipeline` process, so this is not multiple-process colocation and the configured `require_memory_fraction_for_colocation=True` branch does not require explicit per-stage budgets. `_attach_process_memory_fraction_defaults` sees missing fractions and does not inject cumulative process fractions. `_apply_total_reserve_cap` does nothing because no total reserve is set. The TTS builder independently supplies SGLang `mem_fraction_static=0.85`; the vocoder loads Flow and HiFT in the same process and allocator. Exact resident bytes and pool partitioning require runtime evidence. Sources: `config/placement.py:56-162,223-253`; `config/topology.py:404-476`; `pipeline/mp_runner.py:236-264`; `pipeline/stage_workers.py:818-893`; `models/fun_cosyvoice3/engine_builder.py:51-65`.

Per-request memory/state owners are separate maps: coordinator request/future/stream/partial state; each `Stage` active/aborted/binding/stream-counter sets and input/stream queues; each scheduler's request state; and transport allocations in `CommEngine` (external boundary). Stage completion calls `_clear_request_state`, which cancels fan-in state, closes its stream queue, clears counters/target sets/bindings, and removes the active ID. Abort additionally invokes comm cleanup and scheduler abort. Direct local dispatch does not clone the payload; multi-target local payload routing only permits a projected object after checking that it is a distinct `StagePayload.data` graph without shared mutable dict/list/set/bytearray containers. Sources: `pipeline/coordinator.py:60-131`; `pipeline/stage/runtime.py:87-169,1353-1437,1710-1790`; `pipeline/stage/input.py:42-140`; `pipeline/stage/stream_queue.py:32-128`.

## Edges, streaming order, and execution scheduling

The static CosyVoice graph contains payload edges `preprocessing -> tts_engine -> vocoder` and stream edge `tts_engine -> vocoder`. `_resolve_same_process_targets` includes both downstream targets because all stages are non-TP members of the same compiled process. There are no default relay-backed pipeline edges and no remote-stage entries. Sources: `models/fun_cosyvoice3/config.py:32-96`; `pipeline/mp_runner.py:83-233,267-296`.

`preprocessing -> tts_engine` uses local object dispatch: it is a single payload target, has no stream relationship, and therefore passes `_can_send_full_payload_locally`. `tts_engine -> vocoder` stream chunks use direct local dispatch and mark the target local for that request. When the TTS result arrives, `_route_result` first sends `stream_done` to the vocoder, then routes the full result payload. Because the stream target was local, the payload is also eligible for local object dispatch. Each local call directly awaits the target's receive method; chunk, done, and payload handlers synchronously enqueue corresponding scheduler messages. Sources: `pipeline/stage/runtime.py:1171-1350,1427-1653`; `pipeline/local_dispatch.py:36-88`.

The vocoder is explicitly `can_accept_stream_before_payload=True`. Its stage has a `StreamQueue(max_pending=4096)`, though the implementation's per-request asyncio queues are unbounded and `_max_pending` is not used for admission. A first pre-payload chunk or done opens the request's queue and is forwarded into the vocoder scheduler inbox. Without that flag, the stage aborts its scheduler request and sends failure. Sources: `models/fun_cosyvoice3/config.py:72-96`; `pipeline/stage_workers.py:806-809`; `pipeline/stage/runtime.py:745-763,893-949`; `pipeline/stage/stream_queue.py:32-128`.

For nonlocal `DataReadyMessage` traffic, `Stage._schedule_receive_task` creates a task per message but chains a per-`(request_id, from_stage)` predecessor future. Transport reads can overlap, while delivery waits for the predecessor so chunk/data/signal delivery order is retained within that source lane. Different source lanes can progress independently. Direct process-local calls bypass these receive tasks and run in the single worker loop in awaited call order. Sources: `pipeline/stage/runtime.py:389-442,462-729,880-933`.

Stage-to-scheduler execution is always queue based. Submit/payload creates `IncomingMessage(type="new_request")`; chunks create `stream_chunk`; done creates `stream_done`. The worker-loop outbox drain uses `run_in_executor` for blocking queue get, drains at most 64 immediately available records before `await asyncio.sleep(0)`, and ignores scheduler outputs for request IDs no longer active. Sources: `pipeline/stage/runtime.py:444-596,893-971,1092-1169`.

The vocoder's streaming scheduler can accept chunks before payload, latches stream contract metadata, and holds per-request stream state. The base defers done received before payload in `_pending_done`; payload arrival then processes the pending done. Fun-CosyVoice3 enables cross-request chunk batching and distinct-request selection; its factory defaults are batch size 16, 30 ms non-streaming batch wait, Flow admission cost 8000 frames, initial hop 25 and maximum hop 100. These scheduler mechanics are direct-owner dependency facts; detailed Flow/HiFT numerical computation belongs to the model-compute sector. Sources: `scheduling/streaming_simple_scheduler.py:34-551`; `scheduling/streaming_vocoder.py:94-513`; `models/fun_cosyvoice3/config.py:72-94`.

## CUDA execution facts and unresolved stream count

The child sets current device 0 before constructing both GPU stages. Each scheduler thread also sets device 0 before calling scheduler `start`. Both GPU schedulers and the preprocessing executor's CUDA-capable global model resources therefore operate in the same process CUDA context. The pipeline runtime itself does not create a `torch.cuda.Stream`. Sources: `pipeline/stage_workers.py:622-629,896-960`; `pipeline/stage/runtime.py:214-233`.

The TTS builder default sets `disable_cuda_graph=False`, `disable_overlap_schedule=True`, and `enable_torch_compile=False`. It constructs deferred SGLang infrastructure and then initializes SGLang CUDA graphs when the resolved infrastructure requests them. Fun-CosyVoice model setup also constructs two ONNX sessions with an intra-op thread count capped at `min(16, os.cpu_count())`, and installs that context for preprocessing. The vocoder defaults disable both DiT torch compilation and the TensorRT flow estimator. Sources: `models/fun_cosyvoice3/engine_builder.py:18-143`; `scheduling/engine_factory.py:42-236`; `models/fun_cosyvoice3/config.py:49-94`.

No exact CUDA-stream count is statically established by the assigned runtime. Default-stream use, CUDA graph replay streams, ONNX Runtime streams, allocator synchronization, and library-created streams are owned by PyTorch, ONNX Runtime, SGLang, and model internals. A runtime CUDA trace is required to enumerate them. The code does establish that no process boundary separates the TTS and vocoder CUDA work.

## Request lifetime, completion, failure, and cancellation

Admission rejects a reused ID while any request, future, stream queue, or abort task owns it. With default Fun-CosyVoice, `resolve_coordinator_max_in_flight` cannot find both admission keys because the pipeline class supplies no generation-admission defaults and the default engine block has no overrides; it returns `None`, so the coordinator installs no pipeline-wide in-flight cap. The TTS engine still uses its builder/SGLang request limits. Sources: `pipeline/mp_runner.py:51-80`; `pipeline/coordinator.py:405-518`; `models/fun_cosyvoice3/config.py:49-71`.

Admission creates `RequestInfo(PENDING)`, a completion future, optional stream queue, and the initial `StagePayload`, then sends `SubmitMessage` and changes state to `RUNNING`. Replica bindings are absent in this one-replica default. Non-streaming `submit` awaits the future and always removes its future mapping afterward. Streaming iteration yields stream messages and the terminal completion; if the generator exits while the request remains active, its `finally` awaits coordinator abort and then removes stream/future ownership. Sources: `pipeline/coordinator.py:352-518`; `pipeline/replicas.py:253-278`.

Successful vocoder completion resolves immediately because there is one expected terminal. It sets result, resolves the completion future, enqueues completion for a streaming caller, and removes `_requests`. A failure from any active stage marks failed, broadcasts abort, rejects/cancels the future according to caller type, enqueues failure for streaming, clears partials, and removes the request. Unknown or inactive completions are ignored. Sources: `pipeline/coordinator.py:603-758`.

`Coordinator.abort` deduplicates concurrent aborts with one strongly held task and shields it from caller cancellation. `_run_abort` broadcasts the request ID, marks aborted, rejects the nonstream future or enqueues a failed completion for a stream, then removes request and partial state. At each stage, the abort listener records a bounded aborted-ID tombstone, cleans transport state, clears stage request state, and calls scheduler abort. Messages already in transit are drained/discarded and relay transfers are acknowledged where applicable. Sources: `pipeline/coordinator.py:520-601`; `pipeline/stage/runtime.py:816-878,1761-1790`.

Runner shutdown marks `_started=False` before entering cancellation-resistant teardown. Default shutdown sends shutdown to all registered stages, joins the one child up to 30 seconds, then terminates and eventually kills a stuck child, cancels the coordinator completion loop, stops the coordinator, clears groups, and deletes its per-run IPC directory. Stage shutdown stops its scheduler, waits up to five seconds for the scheduler thread, closes control/TP/comm resources, and clears receive tasks. Sources: `pipeline/mp_runner.py:452-471,784-906`; `pipeline/stage_workers.py:378-403`; `pipeline/stage/runtime.py:252-318`; `pipeline/runtime_config.py:48-73`.

## Profiler dispatch and observability

`ProfilerControlClient` connects a PUSH socket directly to each registered stage endpoint and sequentially sends start/stop control messages to selected stages or all endpoints. The coordinator is not in this dispatch path. In a TP stage, the leader fans profiler controls to followers; default CosyVoice has no TP followers. Sources: `profiler/profiler_control.py:12-87`; `pipeline/stage/runtime.py:320-373`.

Each stage handles profiler messages on its shared worker asyncio loop. Start optionally creates a torch trace template suffixed with the worker PID and starts the process-global platform profiler if it is inactive; it separately starts the event recorder for that stage. Since all default CosyVoice stage endpoints enter the same process, each message has the same PID suffix. Whether the profiler implementation can represent simultaneous stage starts is an external platform-profiler contract; this handler only starts when inactive. Stop accepts `run_id=None` as wildcard and stops only matching active profiler/recorder runs. Sources: `pipeline/stage/runtime.py:1792-1823`.

Pipeline events include request admission, stage input, aggregate readiness, dispatch, stage hops with chosen transport, first and subsequent stream chunks, stage completion, terminal response, and coordinator stream receipt. Communication traces for inline/direct CUDA IPC stream branches are emitted by the stage; relay trace ownership is external. Logs expose process spawn/PIDs, process readiness, registered endpoints, stage/device mapping, scheduler crashes, child death, shutdown escalation, admission rejection, and request completion/abort paths. Sources: `pipeline/coordinator.py:405-492,623-758`; `pipeline/stage/runtime.py:444-596,1171-1708`; `pipeline/stage_workers.py:272-365`.
