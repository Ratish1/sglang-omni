# Sector 05 — SGLang bridge and Fun-CosyVoice3 autoregressive integration

## Scope and baselines

This report describes code mechanics only. The Omni baseline is `645b472cd`; the upstream SGLang checkout is exactly `0bcd822377da7b5718e674eaf9c870d349424dd1` (`v0.5.19`). Every assigned Omni file was read in full. Direct owner files needed to close the CosyVoice request, sampling, and output contracts were also read in full. Large generic scheduler and CUDA-graph owner files were read only at the listed ranges; those gaps are explicit under “Evidence boundaries.” No tests, model runs, benchmarks, or package installs were performed.

## Reachable ownership and call graph

The default pipeline places preprocessing and `tts_engine` in the pipeline process and the vocoder after it. `FunCosyVoice3PipelineConfig` supplies `dtype=bfloat16`, `token_hop_len=25`, and no async-decode option (`sglang_omni/models/fun_cosyvoice3/config.py:32-95`). `create_sglang_tts_engine_executor` constructs `FunCosyVoice3EngineBuilder` and calls `build` (`sglang_omni/models/fun_cosyvoice3/stages.py:793-816`).

The concrete ownership chain is:

1. `SGLangGenerationEngineBuilder.build` resolves the checkpoint and device, merges generation defaults and operator overrides, creates resolved `ServerArgs`, builds SGLang infrastructure with graph capture deferred, runs CosyVoice model setup, captures requested generation graphs, then creates `SGLangOutputProcessor`, `FunCosyVoice3ModelRunner`, request/result adapters, and `OmniScheduler` (`sglang_omni/scheduling/engine_factory.py:56-240`, `335-362`, `494-519`).
2. `create_sglang_infrastructure` creates `ModelWorker`, allocates the request/KV pools, initializes attention backends, optionally initializes graphs, and creates the prefix cache (`sglang_omni/scheduling/bootstrap.py:105-219`). The deferred wrapper returns whether graphs were requested (`bootstrap.py:237-257`).
3. `ModelWorker` resolves the SGLang model config, publishes the process-global runtime context, initializes backend globals, then constructs `SGLModelRunner`; after runner construction it derives and broadcasts the random seed (`sglang_omni/model_runner/model_worker.py:61-100`). `SGLModelRunner` registers Omni architectures before invoking upstream `ModelRunner.__init__` (`sglang_omni/model_runner/sglang_model_runner.py:236-309`, `565-611`).
4. Cosy setup loads `llm.pt` to CPU, calls the model’s weight loader, constructs the HF tokenizer and two ONNX sessions, and publishes the preprocessing context (`sglang_omni/models/fun_cosyvoice3/engine_builder.py:79-124`). The builder then creates the runner/adapters and connects the runner’s stream outbox to the scheduler (`engine_builder.py:126-143`).
5. Preprocessing creates prompt embeddings and content-derived placeholder IDs, then stores the heavy prepared object in a process-local map keyed by request ID (`request_builders.py:626-739`). Admission pops that one-shot object, creates SGLang `SamplingParams` and `Req`, and wraps both in `CosyVoice3SGLangRequestData` (`request_builders.py:742-817`).
6. `OmniScheduler` delegates admission and batch policy to upstream scheduler methods but owns execution bridging. It creates a non-speculative `FutureMap`, binds `SGLangExecutionBridge`, and routes each batch through `ModelRunner.execute` by default (`sglang_omni/scheduling/omni_scheduler.py:167-180`, `445-458`, `524-552`, `1438-1454`). Upstream `process_batch_result` then appends the sampled token to `Req.output_ids`, updates finish state, manages KV ownership, and calls Omni’s `stream_output` (`sglang_omni/scheduling/omni_scheduler.py:1423-1428`; upstream `scheduler.py:4357-4387`, `batch_result_processor.py:240-370`, `878-1017`).
7. At terminal completion Omni flushes runner-buffered codec chunks, copies final SGLang output history and finish reason into request data, applies the model result adapter, clears generic embed state, detaches request ownership, and enqueues the result (`omni_scheduler.py:1628-1737`).

## Exact SGLang reuse and Omni adaptations

`sglang_omni/vendor/sglang/core.py` is a pure re-export boundary for upstream `ModelConfig`, `Req`, `ScheduleBatch`, `PrefillAdder`, `GenerationBatchResult`, `ForwardBatch`, upstream `ModelRunner`, `ServerArgs`, `PortArgs`, `get_global_server_args`, `envs`, and attention-backend choices (`core.py:8-35`). `distributed.py` similarly re-exports tensor-parallel rank/world-size/all-reduce, and `utils.py` re-exports utility predicates plus `LazyValue`, `add_prefix`, and `make_layers`; neither changes behavior (`distributed.py:8-22`; `utils.py:8-32`). The CosyVoice implementation imports its direct Qwen2, logits, weight-loading, `Req`, `SamplingParams`, and `GenerationBatchResult` symbols from upstream rather than these wrappers (`sglang_model.py:9-13`; `request_builders.py:17-18`; `model_runner.py:8-12`).

Two wrappers do patch upstream process state:

- Importing `vendor/sglang/layers.py` saves `RMSNorm.forward_cuda` and assigns `_patched_forward_cuda` globally. An empty `x` returns `x`, or `(x, residual)` when a residual was supplied, folding `post_residual_addition` into residual. A residual or post-residual dtype different from `x.dtype` routes to `forward_native`; all other calls use the saved CUDA implementation (`layers.py:42-84`). Qwen2 constructs upstream `RMSNorm` objects (`upstream qwen2.py:237-312`, `315-446`), so this process-global patch can affect the Cosy backbone once the wrapper is imported. Registration eagerly imports the model modules in registry order and those modules import this wrapper (`sglang_model_runner.py:565-600`), although successful import of every optional model module is runtime-dependent.
- Importing `vendor/sglang/models.py` replaces `sglang.srt.models.utils.apply_qk_norm` globally. Its wrapper forces `allow_inplace=False` only when `q_norm.cast_x_before_out_mul` is true, then delegates every argument to the saved implementation (`models.py:27-53`). The upstream Qwen2 attention used by CosyVoice applies rotary embedding directly and has no `apply_qk_norm` call (`upstream qwen2.py:202-213`), so this patch is process-visible but not on the inspected Cosy Qwen2 forward.

`vendor/sglang/server_args.py` provides the lifecycle-safe config mutation: before publication it calls upstream `declare_late_resolution`; after the same `ServerArgs` object is published it calls `runtime_context.override` (`server_args.py:15-38`). The Cosy build does not invoke a model-specific override through this function, but generic weight-update and encoder-memory paths can.

`SGLModelRunner` is the substantial upstream subclass. It installs Omni architecture registration, supplies colocated KV-budget accounting, optionally filters weight names by a stage prefix, supports same-GPU IPC sharing, re-seeds the upstream compile-capture flag just before graph initialization, and selects an Omni prefill runner only for Whisper (`sglang_model_runner.py:33-62`, `80-233`, `236-309`, `344-525`, `613-631`). CosyVoice has no `weight_prefix`, no architecture-specific config-map rewrite, no custom prefill graph runner, and no declared weight-sharing behavior in its builder.

## Model and weight semantics

`FunCosyVoice3SGLangModel` subclasses upstream `Qwen2ForCausalLM`. Construction keeps the Qwen2 decoder stack, aliases its text embedding as `text_embed_tokens`, adds a separate `Embedding(6761, hidden_size)` for speech/control IDs, and replaces output projection semantics with a bias-free `Linear(hidden_size, 6761)` (`sglang_model.py:15-38`). Its public `vocab_size` always returns 6761 and ignores writes (`sglang_model.py:40-49`); setup also writes 6761 into `model_runner.model_config.vocab_size` so scheduler/sampler tensors use the same width (`engine_builder.py:89-99`).

On decode, the model embeds `input_ids` with `speech_embedding`. On extend it consumes caller-provided prompt embeddings. Both modes call the inherited Qwen2 decoder stack; extend selects one last hidden row per request using cumulative `extend_seq_lens`, or the final row if lengths are absent. `llm_decoder` produces the complete 6761-way logits and returns upstream `LogitsProcessorOutput(next_token_logits, hidden_states)` (`sglang_model.py:51-91`). This bypasses Qwen2’s inherited `lm_head` and inherited `LogitsProcessor` tail. The Qwen2 stack itself uses supplied embeddings when non-null, otherwise its text embedding, then executes attention/MLP/residual layers and final norm (`upstream qwen2.py:315-446`).

`load_weights` maps `llm.model.model.*` checkpoint names to `model.*`, skips `llm.model.lm_head.weight`, directly loads `speech_embedding.weight` and decoder weight/bias when present, and passes all remaining names—including already-HF-style `model.*`—to upstream Qwen2 loading (`sglang_model.py:93-124`). Setup materializes the full checkpoint state dict in CPU memory via `torch.load(..., map_location="cpu", weights_only=True)`, converts it to an item list, and invokes this loader (`engine_builder.py:96-100`). Direct Cosy tensors use their parameter `weight_loader` if installed, otherwise upstream `default_weight_loader` (`sglang_model.py:109-118`).

## Request construction and generation contract

Prompt preprocessing runs against model device/dtype. Target text is tokenized first; `target_text_token_count` is captured before instruction/reference prompt text is prepended. The text embedding is produced by Qwen2’s text embedding. Reference audio contributes speaker embedding, LLM prompt speech tokens only when `ref_text` is present, and Flow prompt tensors; absent audio produces empty CPU tensors. `build_llm_prompt_embeddings` composes `[SOS, speaker, text, task, prompt speech]`, which is squeezed to `[prompt_tokens, hidden]`, detached, and kept on model device/dtype (`request_builders.py:626-701`). Each embedding row is converted to float32 on CPU and BLAKE2b-hashed into a nonnegative 63-bit placeholder token ID (`request_builders.py:617-623`). Those IDs provide stable cache identity; the model never embeds them during prefill.

Sampling defaults are request-level and distinct from engine defaults. Unless explicitly supplied after implicit public defaults are filtered, Cosy uses sampling enabled, temperature 0.7, top-p 0.8, top-k 20, and repetition penalty 1.21 (`request_builders.py:54-68`, `578-614`, `742-780`). With `do_sample=false`, temperature 0 is passed; upstream `SamplingParams.__post_init__` converts temperature below `1e-6` to 1 and top-k to 1, which makes the batch greedy (`upstream sampling_params.py:97-155`; sampler.py:153-173).

The generated-length contract is based on target text alone: `target=max(target_text_token_count,1)`, default `max_new_tokens=min(2048,20*target)`, and `min_new_tokens=min(2*target,max_new_tokens)`. An explicit max replaces the derived maximum, while the minimum remains capped by it (`request_builders.py:759-776`). All 200 IDs `[6561,6760]` are stop IDs; the null tokenizer reports `EOS_ID=6562`, allowing upstream min-new-token setup to union the same EOS with the stop set without text decoding (`request_builders.py:73-95`, `774-800`). Upstream finish processing checks explicit stop IDs, request EOS IDs, tokenizer EOS and additional stop IDs before the length cap (`upstream schedule_batch.py:1585-1607`, `1721-1761`).

Before `min_new_tokens`, upstream `BatchedMinNewTokensPenalizer` constructs a per-row `-inf` mask for the union of these stop sets and adds it while generated length is below the threshold (`upstream penaltylib/min_new_tokens.py:6-81`). Control tokens can therefore be sampled only after the derived minimum; afterward any control token finishes the request. `FunCosyVoice3ModelRunner._collect_tokens` ignores every sampled ID at or above 6561, so terminal/control IDs enter `Req.output_ids` and determine finish state but never enter `output_codes` (`model_runner.py:96-116`; upstream batch_result_processor.py:288-346`, `928-963`).

The request data aliases `data.output_ids` to `Req.output_ids` at creation (`request_builders.py:791-813`). `output_codes` is a separate list of one-element CPU `torch.long` tensors. Final adaptation stacks these, normalizes to `long`, copies them to CPU, and records prompt/completion counts and wall-clock engine time (`request_builders.py:820-850`).

## Forward, sampling, penalties, and materialization

For each scheduled batch, `ModelRunner.execute` enters the execution bridge with an isolated forward-only sampling copy, builds `ForwardBatch`, performs model-specific forward and sampling, publishes GPU next tokens, exits the isolated context, and finalizes host-visible output (`base.py:297-349`). `ForwardBatch.init_new` aliases core batch tensors and sampling info, derives request positions and extend metadata, and takes explicit capture-hidden arguments; `capture_hidden_mode=None` lets upstream derive the configured maximum (`base.py:453-491`; upstream forward_batch_info.py:723-963`). Cosy requests do not ask for hidden capture and the engine output processor is built with `capture_hidden=False` (`engine_factory.py:220-224`).

Prefill is custom eager execution. The runner slices each request’s full prompt embeddings by `prefix_len : prefix_len + extend_range.length`, concatenates request slices, and copies/casts them to the forward input device and model dtype (`model_runner.py:185-205`). It initializes attention metadata itself, chooses mRoPE positions only if present, enters `ForwardContext` if the caller has not already done so, and calls the model directly; the returned `GenerationBatchResult` explicitly says `can_run_cuda_graph=False` (`model_runner.py:207-233`; `sglang_execution.py:32-48`). This path does not use `OmniPrefillInputs`; that sidecar exists for standard upstream eager/breakable-prefill dispatch and is cleared after every prefill in the generic runner (`prefill_inputs.py:1-75`; `base.py:493-546`; `sglang_model_runner.py:311-342`).

Both prefill and decode request sample-before-post. `_prepare_and_forward` therefore invokes `_sample_next_token_ids` before `post_prefill`/`post_decode`, and those post hooks collect the same sampled IDs into codec state (`model_runner.py:58-95`; `base.py:493-542`). Sampling first applies model-config codec suppression if configured (none for Cosy), installs row seeds when any request is seeded, enables output logprobs if requested, and delegates to upstream `model_runner.sample` (`base.py:834-869`, `967-1019`).

Upstream sampling first applies grammar/penalty/logit bias, then custom processing and NaN sanitization. Greedy batches use argmax. Non-greedy batches divide logits by temperature in place, apply softmax, and for this engine’s `sampling_backend="pytorch"` sort probabilities, zero ranks outside top-k and cumulative top-p (and min-p if active), then use `torch.multinomial` or seeded Gumbel-max (`upstream model_runner.py:1812-1884`; sampler.py:114-330`, `597-642`, `717-780`). The default Cosy path has top-k and top-p active, min-p zero. Seeded rows use request seed plus position through `murmur_hash32`; mixed seeded/unseeded batches receive request-ID-derived seeds for otherwise unseeded rows so all TP ranks share them (`base.py:871-919`; upstream sampler.py:717-759`). The builder chooses PyTorch specifically, so the bridge’s seeded top-k/top-p rejection for FlashInfer is not reached under defaults (`engine_builder.py:65-77`; `base.py:903-919`).

Repetition penalty is owned by SGLang’s penalizer state, not reapplied by Omni. Before decode, `ScheduleBatch.prepare_for_decode` feeds the most recent committed output ID into the penalizer orchestrator, then allocates one KV slot and increments sequence lengths (`upstream schedule_batch.py:3265-3333`). The repetition penalizer records the configured multiplier at the emitted token column; application multiplies negative logits and divides nonnegative logits at recorded columns (`upstream penaltylib/repetition_penalty.py:18-60`). On extend/retraction, Omni `_restore_output_penalty_history` rebuilds repetition/frequency/presence state from retained `req.output_ids` counts after upstream preparation cleared retraction state (`base.py:194-270`). Async lookahead is allowed only when repetition/frequency/presence penalties, `min_new_tokens`, and custom logit processing are history-free (`base.py:728-750`); Cosy’s default repetition penalty and positive minimum make it ineligible even if a caller somehow enabled async scheduling.

`_collect_tokens` performs one batched `token_ids.tolist()`, which synchronizes/copies CUDA IDs to Python values; it then creates CPU token tensors (`model_runner.py:103-116`). Separately, generic `_ensure_next_token_ids` guarantees report tokens exist and `_publish_next_tokens` hands the device tensor to the bridge (`base.py:622-671`). `SGLangExecutionBridge.publish_next_tokens` copies to the configured device nonblocking only if needed, stashes it in `FutureMap.output_tokens_buf` at request-pool indices, and sets the live `ScheduleBatch.input_ids=None` (`sglang_execution.py:96-118`; upstream overlap_utils.py:598-631). The next forward’s bridge context calls upstream `resolve_forward_inputs`, which performs deferred pinned-CPU prefill H2D or gathers decode IDs from `FutureMap`; staging fields are cleared after consumption (`sglang_execution.py:75-95`; upstream overlap_utils.py:87-120`).

After bridge publication, `_finalize` invokes `SGLangOutputProcessor`; absent a separately staged host tensor it calls `.tolist()` on `next_token_ids`, creates one `RequestOutput` per row, advances Omni’s `generation_steps`, and returns a `ModelRunnerOutput` carrying both report IDs and graph status (`base.py:575-620`; `sglang_backend/output_processor.py:29-62`). Omni converts this back to upstream `GenerationBatchResult` for upstream state/KV/finish handling (`omni_scheduler.py:1509-1525`). For Cosy, `_collect_tokens` already caused the host materialization; output processing calls `.tolist()` again on the same tensor unless a generic host stage exists.

## Launch/resolve path and lifetime

The default Fun-CosyVoice factory does not pass `enable_async_decode`; `OmniScheduler` therefore uses its default `False`, and the pipeline executes the synchronous path (`engine_factory.py:376-410`; `omni_scheduler.py:182-210`, `1775-1778`). `disable_overlap_schedule=True` is a resolved SGLang server setting, and Omni’s separate `enable_overlap` constructor default is also false (`engine_builder.py:65-77`; `omni_scheduler.py:199-201`). The launch/resolve code remains part of the generic bridge but is not reachable under the inspected default pipeline configuration.

When enabled by another builder, launch is decode-only. It isolates sampling state, builds/forwards, calls `post_decode_launch`, guarantees a sampled ID, publishes it to FutureMap, records an event on the producing stream, then copies `ScheduleBatch` and returns `_PendingStep` holding all tensors and routing state alive (`base.py:351-412`). The base launch hook samples if necessary and async-copies IDs into alternating pinned host buffers; the two buffers prevent launch N+1 from overwriting resolve N (`base.py:122-181`, `272-295`, `768-790`). Resolve queries the event, synchronizes on a miss, skips rows already finished/retracted in a lagged step, runs the resolve hook, and finalizes (`base.py:414-451`, `792-808`). Counters `_async_query_hit` and `_async_query_miss` expose event readiness, not host-copy overlap (`base.py:107-120`, `414-430`).

The scheduler loop launches the current step before resolving the prior one. Explicit drains occur at prefill/extend transitions, while paused, around selected administrative operations, and before low-batch synchronous fallback; the run loop's shutdown/finally path does not itself call `_resolve_pending_async`. After a drain, already finished/retracted lagged rows are dropped before upstream result processing to avoid duplicate emission/KV release (`omni_scheduler.py:1988-2062`, `2408-2647`). The bridge explicitly refuses speculative decoding and does not publish `new_seq_lens` (`sglang_execution.py:54-73`, `107-114`). It is single-stream because Omni refuses its upstream-style overlap loop (`sglang_execution.py:16-20`; `omni_scheduler.py:2381-2397`).

Cosy’s subclass does not override launch/resolve hooks. If async were externally wired, the base launch collects only through `post_decode_launch`; Cosy’s codec collection is implemented in `post_decode`, not `post_decode_resolve` (`model_runner.py:67-74`; `base.py:768-808`). This is a factual method-dispatch boundary; no default Cosy configuration enables that route.

## CUDA graph scope, defaults, capture, and padding

Cosy engine defaults are: `max_running_requests=32`, decode graph maximum 32, torch-compile maximum 32, graphs enabled, overlap disabled, torch compile disabled, static memory fraction 0.85, max prefill tokens 4096, PyTorch sampling, and trusted remote code (`engine_builder.py:60-77`). Shared policy emits decode buckets `[1,2,4,8,12,16,24,32]` from the default ladder and validates that the maximum equals and covers `max_running_requests` (`generation_batch_policy.py:42-54`, `116-234`, `237-313`). Legacy decode keys are translated to SGLang phase-specific keys before `ServerArgs` construction (`sglang_backend/server_args_builder.py:13-36`, `67-102`). CPU placement forcibly disables graphs (`engine_factory.py:81-86`).

Prefill graph backend defaults to disabled at the shared builder unless a model/operator opts in (`server_args_builder.py:93-96`). Cosy does not set `supports_breakable_prefill_cuda_graph` and does not specify a prefill backend, so its reachable prefill is eager. Even if a generic prefill runner existed, Cosy custom prefill bypasses `ModelWorker.forward_batch_generation` and explicitly reports eager (`model_runner.py:48-56`, `207-233`). Shared policy only permits a requested breakable backend for builders that declare support (`engine_factory.py:165-174`).

Upstream graph setup always constructs `EagerRunner` first, captures or resolves prefill before decode, and, when the resolved prefill backend is disabled, assigns that eager runner to ordinary target prefill without constructing `PrefillCudaGraphRunner` (`upstream cuda_graph_setup.py:173-267`, `284-317`). In the Cosy route this reinforces two separate boundaries: startup has no prefill capture, and runtime goes through `custom_prefill_forward` rather than the upstream eager runner's standard extend dispatch. The fully read upstream prefill runner supports breakable, full, and torch-compile-piecewise backends; it owns stable token/request buffers, attention-metadata refresh, capture-bucket selection, padded replay, transformer-body-only capture with an eager logits tail for breakable/full, and output trimming (`upstream prefill_cuda_graph_runner.py:1-1921`). None of those runner methods are reached by the resolved Cosy prefill configuration.

Decode graph capture is upstream-owned. Its bucket list is filtered by attention alignment and request-pool capacity; capture initializes one graph per surviving bucket. Replay admits a non-spec decode when batch size is at most maximum (unless padding is disabled, where an exact backend key is required), selects the smallest bucket at least as large as the live batch, fills stable buffers, and returns outputs sliced to live sizes (`upstream base_cuda_graph_runner.py:64-101`, `135-150`; decode_cuda_graph_runner.py:209-390`, `676-751`, `1325-1495`). The placeholder FutureMap row 0 mirrors KV padding semantics so padded request indices are harmless (`upstream overlap_utils.py:250-289`). Cosy’s model output shape is request-major after its decode forward, matching graph report-token rows.

For completeness, shared prefill policy constructs aggregate-token ladders, caps/extends/trims them against explicit operator values, rejects bucket gaps only as warnings, and treats more than 2x token padding as eager fallback (`generation_batch_policy.py:57-74`, `116-234`, `316-393`). Upstream prefill runner likewise rounds to the next token bucket, rejects more than 2x padding, and for breakable capture preserves the live request axis while copying token-aligned inputs to static buffers; full capture additionally pads request slots with zero-length sentinels (`upstream prefill_cuda_graph_runner.py:273-360`, `1132-1248`, `1521-1752`). These mechanics are not reached by the default Cosy custom prefill.

Graph initialization happens after Cosy weights/tokenizer/ONNX setup because infrastructure defers capture whenever graphs are wanted; `setup_model` runs before `init_sglang_cuda_graphs` (`engine_factory.py:175-202`). It happens before model-local resource setup and before runtime/scheduler construction (`engine_factory.py:211-237`). `init_cuda_graphs` re-verifies weight-sharing attachments if present, re-seeds the torch-compile capture flag from the resolved exec bag, installs per-runner prefill dispatch, delegates upstream capture, and then finalizes virtual-memory KV backing if active (`sglang_model_runner.py:444-480`).

## CPU/GPU state, lifetime, and initialization memory order

The model weights and both added embedding/projection modules reside on the SGLang runner device after upstream loading. Fine-tuned checkpoint deserialization is explicitly CPU-first; the item list/state dict remains referenced only during setup (`engine_builder.py:96-100`). Text/prompt embeddings are generated and retained on GPU in `CosyVoice3PreparedRequest`, while reference artifacts cached by `ReferenceEncodeService` are cloned to CPU for storage (`request_builders.py:302-330`, `626-701`). Prepared requests are process-global and lock-protected; admission pops them, abort removes them, and resetting the preprocessing context clears the entire map (`request_builders.py:342-416`).

The ONNX speech tokenizer and speaker encoder are created during `setup_model` with a per-session intra-op thread count clamped to `[1, os.cpu_count()]` and live for the preprocessing context’s process lifetime (`engine_builder.py:31-48`, `102-124`). Reference encoding loads 16 kHz and 24 kHz host audio, executes the encoders, aligns Flow frames at two frames/token, and stores CPU clones in the cache (`request_builders.py:277-330`, `419-433`, `556-575`). Exact ONNX execution-provider placement is owned by `fun_cosyvoice3/utils.py` and was outside this sector’s assigned surface.

The stage’s startup allocation order is exact: resolve/publish config → upstream runner construction and model weight load → optional hidden-capture hooks → model-specific `before_memory_pool` callback → KV/request pool allocation → attention backend initialization → deferred graph return → Cosy `setup_model` and fine-tuned weight replacement plus long-lived preprocessing resources → generation graph capture → model resources → output processor/runtime resources → scheduler (`model_worker.py:61-100`; `bootstrap.py:105-219`; `engine_factory.py:175-237`). Cosy uses `setup_model`, not `before_memory_pool`, so its `llm.pt` replacement and ONNX objects are created after KV pool sizing. This is the observed lifecycle order, without a claim about runtime peak memory.

A declared stage `kv_cache_bytes` travels through a thread-local one-use scope. Missing consumption and double consumption are errors (`stage_kv_budget.py:20-88`). The explicit-byte configurator checks positive size, rejects mamba/hybrid use, checks currently free bytes, and returns the byte budget directly; fraction-based colocated sizing uses NVML process bytes or the stage-local load delta (`sglang_model_runner.py:80-233`). Without an explicit stage budget it delegates upstream profiling. Post-capture resizing may not silently shrink an explicit byte-sized pool (`sglang_model_runner.py:482-508`).

Per request, placeholder IDs begin as CPU `long`, while prompt embeddings remain GPU model dtype (`request_builders.py:684-699`). Upstream extend preparation stages IDs in pinned CPU memory and defers H2D to forward entry (`upstream schedule_batch.py:2504-2539`, `2697-2709`; overlap_utils.py:87-109`). Cosy prefill slices the retained GPU prompt tensor and passes it directly to the model. Decode IDs are GPU FutureMap state until `_collect_tokens` materializes them; codec output tensors and stream payloads are CPU. Flow prompt tensors originate in cached CPU artifacts and are attached to the first stream metadata payload (`model_runner.py:156-183`). Terminal adaptation ensures final codes are CPU (`request_builders.py:820-850`).

## Prefix cache and request/KV ownership

`create_tree_cache` constructs upstream `CacheInitParams` from the published memory/schedule bags. Radix disabled selects upstream `ChunkCache`; LRU selects Omni `EvictHeapRadixCache`; other policies select upstream `RadixCache` (`sglang_backend/cache.py:13-43`). The Omni LRU subclass persists a heap across calls, lazily rejects stale priorities/nodes, frees the leaf’s complete page-aligned KV segment, deletes the leaf, records a KV remove event, and updates eviction metrics (`evict_heap_radix_cache.py:17-76`).

Prompt placeholder hashes participate in SGLang prefix matching because they are `Req.origin_input_ids`. The actual prompt embedding slice is indexed by the matched `prefix_indices`, so a cache hit skips matching rows in both KV allocation and composed embeddings (`request_builders.py:617-623`, `687-699`; `model_runner.py:190-205`). On normal prefill completion upstream appends the first sampled token and either releases finished KV or caches the unfinished request (`upstream batch_result_processor.py:315-346`). Decode completion extends `Req.output_ids`, updates finish state, and delegates finish/KV handling before streaming (`batch_result_processor.py:928-1008`).
