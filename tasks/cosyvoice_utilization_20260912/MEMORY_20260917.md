# Where the 24 GB goes, and why a 0.5B model runs out of it

Measured 2026-09-17 on the moss box, card 5, RTX 4090 D 23.52 GiB, head
`84e745ea` (slice 1.2 on slice 1.1 on main `27a8293c`). Numbers are the server's
own startup log, not an estimate.

## The accounting

Stages are built in list order and the vocoder comes first, deliberately, so that
SGLang sizes its pool from what is left (`config.py:144-146`). That makes the
first line below the one everything else is measured against.

| taken by | GB | how it is known |
|---|---|---|
| Flow CUDA graphs, 54 captured shapes | **7.66** | avail mem at "Load weight begin" is 13.41 GB by default and 21.07 GB with `enable_flow_cuda_graph false`, same boot otherwise |
| Flow and HiFT weights, ONNX sessions, CUDA context | 2.45 | 23.52 minus 21.07 |
| AR weights | 0.61 | "Load weight end ... mem usage=0.61 GB" |
| AR KV pool | **9.78** | "KV Cache is allocated ... #tokens: 854232, K size: 4.89 GB, V size: 4.89 GB" |
| AR decode CUDA graphs | 0.13 | "Capture target decode CUDA graph end ... mem usage=0.13 GB" |
| left over | 1.36 | "avail mem=1.36 GB" |

Two of those six rows are the problem, and neither is the Flow hop.

## 1. The KV pool is not bounded by the workload, only by free memory

`FunCosyVoice3EngineBuilder.generation_defaults` sets `mem_fraction_static: 0.85`
and, on CUDA, no token cap (`engine_builder.py:114-126`). The MLX and Torch MPS
branches of the same function both set `max_total_tokens: self.context_length`
(`:94`, `:108`); the CUDA branch does not.

The same file sets `context_length = 4096` (`:29`) and
`max_running_requests: 32` (`:115`). Those two bound what the engine can ever
address: 32 x 4096 = **131,072 tokens**, about 1.5 GB at this model's 12.0 KB per
token. The pool allocated **854,232 tokens, 9.78 GB**, 6.5 times the ceiling the
configuration already declares.

It is also elastic in the wrong direction. Freeing memory elsewhere does not
become headroom, it becomes more pool: with the Flow graphs off, the same boot
allocated **1,423,618 tokens, 16.3 GB**. Every byte reclaimed anywhere on the
card is swallowed by a pool that cannot use it.

This is what the request failures are. At c4, 1 of 32 requests fails; at c8, 9 of
32, on code with no hop cache in it. The failure is the reference encoder's ONNX
speech tokenizer being unable to create a cuBLAS handle
(`request_builders.py:296` to `utils.py:92`, "CUBLAS failure 3: the resource
allocation failed"), because 1.36 GB is what the pool left for every ONNX
session, every cuBLAS and cuDNN workspace and every transient allocation in the
sampler.

## 2. Streaming never replays the 54 Flow CUDA graphs

`generate_flow` consults the graph runner only when the call is neither streaming
nor a non-final chunk: `if streaming or not finalize or flow.cuda_graph_runner is
None` takes the eager solve (`stages.py:656`), and the runner is reached only
past that line (`:667`).

Three call sites reach `generate_flow` or its packed sibling:

| caller | line | path | graph |
|---|---|---|---|
| `inference`, buffered | `stages.py:778` | `generate_flow` | yes |
| `inference_causal`, every streaming hop | `:814`, `:816` | `generate_flow(streaming=True)` or `generate_flow_packed` | no, either way |
| `inference_leftover`, every streaming final | `:797` | `generate_flow_packed` | no |

So a streaming request never replays one. On a streaming workload the capture
table is 7.66 GB of resident memory that is written once at startup and never
read, a third of this card.

Measured at c1, 16 samples, same head, same card, streaming:

| | graphs on | graphs off |
|---|---|---|
| RTF mean | 0.2441 | 0.2350 |
| first audio mean | 0.585 s | 0.568 s |
| req/s | 0.834 | 0.867 |

Turning them off is not slower. It frees 7.66 GB.

## Why the pool is that size, read in the pinned SGLang v0.5.19

`mem_fraction_static` does not do what its name suggests. It never multiplies
free or total memory. Its complement multiplies a single earlier free-memory
reading to form a slack term, and the pool takes everything else
(`mem_cache/kv_cache_configurator.py:2007, 2021`):

```python
slack_gb = pre_model_load_memory * (1 - get_schedule().mem_fraction_static)
rest_memory = available_gpu_memory - slack_gb - mm_reservation_gb
```

So lowering the fraction only grows a 2 GB slack; it cannot bound the pool. The
only upper bound is `max_total_tokens`, applied as a `min()` against the profiled
value (`kv_cache_configurator.py:2082-2091`, `server_args.py:699-712`). Nothing
in that revision caps the pool by what the model could address:
`context_len` does not appear in the sizing arithmetic at all, and the
relationship runs the other way, the pool capping `max_running_requests`
(`kv_cache_configurator.py:2109-2118`).

The reading is live driver free memory at the moment of the call
(`utils/common.py:437`), so everything the vocoder stage allocated first is
already charged against it, and nothing is reserved by name for the sampler, for
cuBLAS and cuDNN workspaces, or for ONNX Runtime creating a handle later.

## The fix already exists in Omni and this pipeline does not use it

`engine.kv_cache_bytes` on a stage becomes the KV pool budget directly, with an
explicit free-memory check (`model_runner/sglang_model_runner.py:117-144`,
delivered through `scheduling/stage_kv_budget.py` and `scheduling/bootstrap.py:147`).
Qwen3-Omni requires it per stage (`models/qwen3_omni/placement.py:132-139`).
The Fun-CosyVoice3 pipeline declares no `engine` block at all, so its engine
falls back to profiling and takes the card.

Measured 2026-09-17, card 4, c8, 32 samples, streaming, hop cache off, the only
change being `--tts_engine.engine.kv_cache_bytes 2147483648`:

| | default | 2 GiB declared |
|---|---|---|
| completed requests | 23 of 32 | **32 of 32** |
| failed requests | 9 | **0** |
| CUBLAS handle failures in the log | 20 | **0** |
| KV pool | 9.78 GB, 854,232 tokens | 2.00 GB, 174,762 tokens |
| avail mem after the pool | 1.94 GB | **9.71 GB** |
| req/s | 2.214 | 2.484 |
| audio s/s | 10.148 | 11.602 |

The speed columns are not a like for like comparison, because the default arm
completed 23 requests and this one completed 32. The columns that matter are the
first two.

A default that needs no tuning: `max_running_requests` x `context_length` x the
model's 12,288 bytes per token is 32 x 4096 x 12,288 = 1.61 GB, and the scheduler
cannot admit more than that by construction. Measured peak occupancy is far
below it: 1,725 tokens at c8 and 929 at c4, from the decode log's `#token` field,
against a pool of 854,232.

## What this says about the optimization work

The whole task ranked its work from a profile of where the vocoder step's *time*
goes. Nobody profiled where the card's *memory* goes. The result is that roughly
16 GB of a 23.5 GB card is committed to a pool that is 6.5 times its own
configured ceiling and a graph table that streaming traffic never touches, while
the plan spent its effort on a hop cache measured at 3 percent at c1.

The hop cache is not wrong. It is the third thing, not the first.
